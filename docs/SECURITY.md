# ClawdMeter security

This document gathers the app's security model: what Rust lets the webview do, the process and tool policy for skills, the capabilities, the CSP and the known open items. For the product overview, see the [README](../README.md); for the architecture, [ARCHITECTURE.md](ARCHITECTURE.md).

Summary: everything runs locally; the app only talks to `api.anthropic.com`, `api.github.com` (plus GitHub's release-asset storage for update downloads) and `graph.microsoft.com`; the Claude Code credential is read in read-only mode, never refreshed and never handed to the webview.

## Rust commands (`src-tauri/src/commands`)

Each command has its own permission (`allow-<name>` in `capabilities/default.json`, declared in `build.rs`). Errors reach TS as `{ kind, message }` (`rate_limited` adds `retryAfterSecs`, see below) and become `ConnectionProblemError` (`keychain_denied`, `claude_code_missing`, `claude_expired`) or `PlatformCommandError`. In Rust the type is `CommandError` (`thiserror`, with `From` for `io`, `keyring`, `reqwest`, `tauri` and `url`) and the `kind` is one of: `keychain_denied`, `keychain`, `claude_code_missing`, `claude_expired`, `credential_malformed`, `program_not_allowed`, `program_not_found`, `invalid_argument`, `policy`, `spawn_failed`, `too_many_processes`, `timeout`, `state_mismatch`, `provider_error`, `cancelled`, `http`, `rate_limited`, `tray`, `io`. Commands that block (`process_run`, `oauth_loopback_wait`, `process_kill`, `process_is_alive`, `secret_*`, `claude_*`, `notification_permission_state`) are `async fn` and run the work in `spawn_blocking`, without tying up a runtime worker.

| Module | Commands | Notes |
|---|---|---|
| `secrets` | `secret_get/set/delete` | `keyring` crate (Keychain / Credential Manager), service `com.mottu.clawdmeter`; only the keys in `ALLOWED_SECRET_KEYS` (`github.token`, `microsoft.refresh-token`, mirrored in `SECRET_KEYS` by a test), any other gives `policy`; secrets above 1200 bytes are sliced into `<key>`, `<key>#1`… (Credential Manager limits the blob to 2560 bytes) |
| `claude_credentials` | `claude_credentials_status`, `claude_usage_fetch` | reads the Claude Code credential (Keychain/file) and does the `GET https://api.anthropic.com/api/oauth/usage` (`anthropic-beta: oauth-2025-04-20`, 15 s timeout, response up to 256 KiB, redirects not followed) with the `reqwest` of `tauri-plugin-http`; returns only `{ expiresAt, subscriptionType }` or the usage JSON. An expired credential or 401 gives `claude_expired`; 429 gives `{ kind: 'rate_limited', message, retryAfterSecs }`, with `retryAfterSecs` taken from the `Retry-After` header (seconds or HTTP date `IMF-fixdate`, converted to seconds from now, never negative, capped at 1 hour) and `null` when the header is missing or invalid; the other statuses, 5xx included, follow `http`; a denied Keychain, `claude_code_missing` and `credential_malformed` keep their `kind`. The `http:default` allowlist no longer has `api.anthropic.com` |
| `process` | `process_run/spawn/kill/is_alive` | only `claude` and `gh`, with per-program validated arguments (`process_policy.rs`): `gh auth token [-h github.com]`; `claude -p <prompt> --output-format stream-json [--verbose] --max-budget-usd <n> [--allowedTools <list>]` (the list goes in a single comma-separated argument) and nothing else: `/login`, `/mcp` and `--resume <uuid>` do not go through `process_spawn`, only through `terminal_run`; no `--dangerously-skip-permissions`, `--permission-mode`, `--add-dir` and `--mcp-config`; an explicit `cwd` of `process_spawn` only a project folder (inside the user's folder, with `.git`, outside `~/Library`, `~/.config`, `~/.kube`, `~/.docker`, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.claude`, `~/AppData` and the app's config, data, cache and log folders); without `cwd`, `process_spawn` uses an empty app working directory, `app_cache_dir()/skill-cwd` (created if missing, outside `$APPCONFIG` and outside any webview `fs` scope, which a test checks in `capabilities/default.json`), and only the `gh` `process_run` falls back to the user's folder (on Windows the `\\?\` prefix of the canonical path is removed), never inside the app config directory (`app_config_dir()`, resolved by the `AppHandle`) nor `~/.claude`: on Windows the Tauri `fs` scope accepts dotted paths, so the webview could write `$APPCONFIG\.claude\settings.json` and run claude there; `process_run` only runs `gh` (`claude` only goes through `process_spawn`, which injects the hardening flags); a timeout ends the group; `kill` only for the app's children (an unknown or already ended pid is ignored); on app exit (`RunEvent::Exit`) children still alive are killed; at most 4 simultaneous processes (`too_many_processes`); a spawned run is killed after 15 minutes; when its main process exits, Rust SIGKILLs the rest of its process group before reaping (Windows: the child is in a kill-on-close Job Object that is terminated), so an MCP server or `gh` left behind does not keep running; children get only `PATH`, `HOME`, `USER`, `LANG`, `LC_*`, `TMPDIR`, `SHELL`, `TERM` (Windows also `SystemRoot`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `PATHEXT`, `COMSPEC`, `TEMP`, `TMP`) plus `GH_PROMPT_DISABLED=1`; `process_is_alive` refuses pids above `i32::MAX` (they would become `kill(-1, 0)`); `kill` of a pid that is already exiting is ignored, because the registry marks the pid as "exiting" under the same lock as `kill` before `wait()` does the reap (on Unix the wait uses `waitid(WNOWAIT)`, which leaves the zombie until the mark); the output captured in `process_run` is limited to 1 MiB per stream (with a `[output truncated]` mark) and each stream line to 4 MiB on stdout (`stream-json` carries one event per line, and the `result` can be large) and 64 KiB on stderr (with a `…[line truncated]` mark; TS recognizes the mark on a stdout line that starts with `{` and flags the run with the error "Output truncated: …" instead of the generic "ended without a result"; if an intermediate event is cut but the final `result` arrives intact, the run goes on as completed); `process-output` and `process-exit` events carry `{ id }`, the per-spawn sequence number that `process_spawn` returns and `process_kill` takes, never the pid |
| `oauth_loopback` | `oauth_loopback_listen/wait/cancel` | validates `state`, timeout, local return page; a callback with a wrong or missing `state` gets 400 and the listener keeps waiting, only a provider error with a valid `state` ends it; each connection has a total of 5 s to deliver the header (in addition to 2 s per read), so a client that pings one byte at a time does not hold the listener (the worst delay for a cancel is this deadline, because accept is sequential); interrupted reads (`ErrorKind::Interrupted`) are retried, both here and in the `process_run` capture; at most 2 listeners open at once, and a listener can be awaited only once (it stays in the registry, so `cancel` still reaches a running wait) |
| `terminal` | `terminal_run` | `claude`/`gh` with the same per-program policy (`claude /login`, `/mcp`, `--resume <uuid>`, never `claude -p`; `gh auth login/refresh`) and arguments without shell metacharacters; accepts `cwd` (the run's folder, validated as in `process`, including the refusal of `app_config_dir()` and `~/.claude`, without quotes or backslash); without `cwd` it opens in the user's folder, except `claude --resume <uuid>`, which reopens in `app_cache_dir()/skill-cwd` because `claude` stores the session per directory and the run started there; the program goes by the resolved absolute path (the same `resolve_program` as `process`), inside single quotes like the `cwd`; on Windows a resolved path with `&`, `^`, `%`, `|`, `<`, `>`, `(` or `)` is refused because `cmd /K` would interpret it (an install under `Program Files (x86)` is refused too) |
| `notification_permission` | `notification_permission_state` | `granted`, `denied`, `prompt` or `unknown` |
| `open_external` | `open_url`, `open_system_settings` | only `https` and known panes |
| `updater` | `updater_check`, `updater_install`, `updater_restart` | release lookup, `latest.json` and package download in Rust (`reqwest` of `tauri-plugin-http`, redirects handled hop by hop: token only to `api.github.com`, never to the storage host; other hosts and plain http refused); signature verified by `tauri-plugin-updater` before installing; see Updates below |

HTTP access to GitHub and Microsoft goes through `tauri-plugin-http` (avoids WebView CORS), with a URL allowlist in the capability.

## Capabilities and CSP

Each command has its own permission (`allow-<name>` in `src-tauri/capabilities/default.json`, declared in `build.rs`). The plugin-fs scopes (Claude Code sessions, ClaudeUsageBar history, app config folder) and the plugin-http allowlist are checked by `tools/capabilities.spec.ts`. The CSP in `src-tauri/tauri.conf.json` only allows `self` and IPC. Details and limits in Security open items and Known limitations below and in [ARCHITECTURE.md](ARCHITECTURE.md).

## Launch at login

- **Permissions.** The webview gets only `autostart:allow-enable`, `autostart:allow-disable` and `autostart:allow-is-enabled` (not `autostart:default`, so a new plugin command does not come in on its own); `tools/capabilities.spec.ts` fails if the `autostart:` list changes.
- **Dependency.** `tauri-plugin-autostart` 2.7.0 (MIT/Apache-2.0) and its `auto-launch` 0.6.0 (MIT), which on macOS also pulls `smappservice-rs` (MIT), `objc2-service-management`/`objc2-security` (Zlib/Apache-2.0/MIT) and `os_info` (MIT), on Windows `windows-registry` (already in the tree), plus `dirs` 6 next to the `dirs` 7 already in the tree (a duplicate that `deny.toml` only warns about). JS: `@tauri-apps/plugin-autostart` 2.7.0. `cargo deny check` passes without touching `deny.toml`, and `cargo audit` finds no vulnerability and no new warning (the allowed warnings are the same as before the plugin).
- **What it writes.** macOS: a LaunchAgent plist in `~/Library/LaunchAgents` with the path of the running executable and no arguments; Windows: a `Run` registry value with the `.exe` path. The webview cannot choose the path or the arguments: the plugin fixes both in Rust at setup. Nothing is registered until the user turns the switch on.
- **Limit.** The plugin is not scoped: any script running in the webview can turn launch at login on or off. Same trust level as the rest of the IPC (the CSP only allows `self`).

## Skills policy (`claude -p`)

- **Tools: exact allowlist.** `--allowedTools` only accepts entries identical to those in `ALLOWED_CLAUDE_TOOLS` (`process_policy.rs`, mirrored in `skill-definition.ts` by a test that reads the Rust file): `Read(./**)`, `Bash(gh pr list|view|checks|diff:*)` and `Bash(gh search prs:*)`. The two Jira MCP tools (`mcp__plugin_atlassian_atlassian__searchJiraIssuesUsingJql` and `getJiraIssue`) left the list in round 4, because no MCP server loads any more (see below). `Bash` without a pattern, `Bash(*)`, `Bash(git:*)`, `Bash(gh:*)`, `Read` without a scope, `Write`, `Edit`, any `*` and any other tool are blocked in Rust; in TS the run fails before opening the process with "Skill … uses a tool that is not allowed: …". `Grep` and `Glob` are not in the list: `claude` runs them without a rule inside the run's `cwd` and, outside it, `dontAsk` denies them; an old `skills.json` with `Grep`/`Glob` fails with "Update skills.json". The helper scripts of `/acabativa` (`bash`/`python`) are left out on purpose.
- **`skills.json` migration (round 2).** `Bash(git diff:*)`, `Bash(git log:*)` and `Bash(git status:*)` left the list because `claude` matches the pattern by prefix and the subcommand accepts write flags (`git diff --output=$HOME/.zshrc` writes an arbitrary file); swap for `Bash(gh pr diff:*)` or remove. `Read` became `Read(./**)` (a read rule relative to the run's directory, Claude Code permission rule syntax, not confirmed by running `claude`). A `skills.json` with the old names is still read, but the run fails before opening the process with the message "Skill … uses a tool that is not allowed: …. Update skills.json …". With a null `cwd` the run starts in the app's empty `skill-cwd` folder (round 3), so `Read(./**)` covers only it; a skill that needs to read a project sets its `cwd` in `skills.json`.
- **Flags injected by Rust (round 4).** After validating the argv coming from the webview, `process_spawn` always appends to the end of any `claude -p`, in this order: `--setting-sources "" --settings <app_cache_dir>/claude-settings.json --strict-mcp-config --permission-mode dontAsk --disallowedTools <deny list>` (`prepare_invocation` in `process_policy.rs`; a `claude -p` without the settings file is refused with `policy`). TS does not pass these flags and Rust blocks them if they come from the webview, including in the `--flag=value` form (`--settings`, `--setting-sources`, `--permission-mode`, `--dangerously-skip-permissions`, `--add-dir`, `--mcp-config`, `--strict-mcp-config`, `--disallowedTools`/`--disallowed-tools`).
  - **No user settings (N1).** `--setting-sources ""` loads no `user`, `project` or `local` settings file, so `~/.claude/settings.json` (its `permissions.allow`, hooks, `defaultMode`) no longer applies to skill runs. Checked against the local `claude` 2.1.318: `--help` lists `--setting-sources <sources>` ("Comma-separated list of setting sources to load (user, project, local)"), `--settings <file-or-json>` and `--strict-mcp-config` ("Only use MCP servers from --mcp-config, ignoring all other MCP configurations"); the flag parser in the binary returns an empty list for `""` (`if(e==="")return[]`) and only throws `Invalid setting source` for an unknown name. Managed (enterprise) settings still apply, as in any `claude` run. Not confirmed by running `claude -p`.
  - **App-owned settings file.** Rust rewrites `app_cache_dir()/claude-settings.json` before every spawn (temp file + rename, so a symlink planted there is replaced, not followed): `permissions.allow` = `ALLOWED_CLAUDE_TOOLS`, `permissions.deny` = the deny list, `defaultMode: dontAsk`, `disableBypassPermissionsMode: disable`, `disableAllHooks: true`, `enableAllProjectMcpServers: false`. `app_cache_dir()` is outside every webview `fs` scope (a Rust test checks that the capability never names `$APPCACHE`); `$APPDATA` was not used because on macOS it is the same folder as `$APPCONFIG`, which the webview can write. Since the file's `allow` is the whole allowlist, a skill that passes a narrower `--allowedTools` can still use the other allowlisted tools; the ceiling is the allowlist.
  - **No MCP servers (N1).** `--strict-mcp-config` without `--mcp-config` starts no MCP server: not the user's, not the plugins', not a `.mcp.json` in the run's folder. **The Jira integration of skills (the cards `/acabativa` reads) is off** until the app ships its own `mcp-config` with only the Atlassian server; the skill still runs, without the Jira part.
  - **Project folders only (N2).** An explicit `cwd` must be a git project (a `.git` folder or file) inside the user's folder and outside `~/Library`, `~/.config`, `~/.kube`, `~/.docker`, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.claude`, `~/AppData` and the app's config, data, cache and log folders (compared by whole path components, ignoring case on macOS and Windows). Without `cwd` the run still starts in the empty `skill-cwd`. `terminal_run` keeps the earlier rule (home subfolder, not `~/.claude` or the app config), because `claude --resume` must reopen the folder where the session ran.
  - **Reading of sensitive paths denied (rounds 3 and 4).** `--disallowedTools` (and the settings file's `deny`) carry `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, `WebFetch`, `WebSearch`, `Read(~/.ssh/**)`, `Read(~/.aws/**)`, `Read(~/.config/**)`, `Read(~/.claude/**)`, `Read(~/.gnupg/**)`, `Read(~/.kube/**)`, `Read(~/.docker/**)`, `Read(~/Library/**)` and `Read(~/AppData/**)`. Not confirmed by running `claude`: `--help` only lists the flag and the `Bash(git *)` format, not the `Read(~/…)` rule syntax; it follows the Claude Code permissions documentation (`~/` is the user's folder; a `Read` rule also applies to `Grep` and `Glob`, on a best-effort basis). That is why there are no separate `Grep(...)`/`Glob(...)` rules. Side effect: a skill support file that lives in `~/.claude` and is read through the `Read` tool is also denied.
  - **`gh` variable.** Rust sets `GH_PROMPT_DISABLED=1` in the children's environment, so `gh` never waits for a prompt.
  - **`Bash` outside `--disallowedTools`.** The review asked for `Bash` in the denied list, but deny beats allow in Claude Code: a denied `Bash` would cancel `Bash(gh pr …:*)` and the skill would be left without `gh`. Only the four write tools go in. Residual risk: a skill with `allowed-tools: Bash` in its frontmatter can widen Bash beyond the `gh` patterns.
  - **`process_spawn` only accepts `claude -p` (round 3).** `claude /login` and `claude --resume <uuid>` used to be accepted without the hardening flags; now they are refused (`claude arguments not allowed`) and only run in the interactive terminal.
  - `terminal_run` with `claude` only accepts `/login`, `/mcp` and `--resume <uuid>` (never `-p`), so there is no `claude -p` path that escapes these flags.

## Updates

- **Signature.** Every updater artifact (`.app.tar.gz`, `.msi`, `.exe`) is signed in the release job with the minisign key in the `TAURI_SIGNING_PRIVATE_KEY` secret. The app carries only the public key (`plugins.updater.pubkey` in `tauri.conf.json`) and `Update::install` refuses a package whose signature does not match. `requireSignedVersion: true` (and `restore_update`, which forces it) also requires the version in the signature's trusted comment to equal the version in `latest.json`, so a changed `latest.json` cannot pair a new version number with an older signed package. The private key lives only on the maintainer's machine (`~/.tauri/clawdmeter-updater.key`) and in the Actions secret, never in the repository.
- **Token.** The GitHub token is the one of the GitHub connection (gh CLI, device flow or PAT). It is resolved by `GitHubTokenResolver` like for PRs (so it still crosses the IPC, the debt below) and handed to the `updater_check`/`updater_install` commands; every update request is made in Rust, none through the webview `plugin-http`, so the http capability did not change.
- **No token in redirects.** The asset API answers with a 302 to a signed URL on `release-assets.githubusercontent.com` (or `objects.githubusercontent.com`). The client has `redirect::Policy::none()` and follows each hop itself: `Authorization` is only sent to `api.github.com`, the storage host gets the request without it, and any other host or a non-https URL ends the download with `policy` before connecting (Rust tests with local servers check the header on each side). The package URL itself must be an `api.github.com` asset URL: `updater_check` rewrites every `latest.json` entry to `/repos/<repo>/releases/assets/<id>` of an asset of the same release and drops entries that do not match.
- **Permissions.** The webview gets `allow-updater-check`, `allow-updater-install` and `allow-updater-restart` only; no `updater:*` permission of the plugin, so the plugin's own JS commands are unreachable (`tools/capabilities.spec.ts`).
- **Limits.** Release JSON 1 MiB, `latest.json` 64 KiB, package 300 MiB, at most 3 redirects, 20 s timeout for the check and 15 min for the download. The check runs at most every 6 h and stops while GitHub reports a rate limit.

## Security open items (Rust review)

- **Debt: GitHub and Graph tokens still cross the IPC.** The Claude token no longer leaves Rust (`claude_usage_fetch`), but `secret_get` still returns `github.token` and `microsoft.refresh-token` to the webview, which makes the calls to GitHub and Microsoft Graph through `tauri-plugin-http` and passes the GitHub token back to the `updater_*` commands. Moving those calls to Rust (as was done for usage) is the next step; until then `secret_*` only accepts these two keys.
- **Open item S3 (macOS): Keychain read via `/usr/bin/security`.** If the user picks "Always Allow", access is granted to the `security` binary, not to ClawdMeter, and any local process starts reading the Claude Code credential without a prompt. The fix is to use the native API (`security-framework`), which ties access to the app's signature; today the app is signed ad hoc (`signingIdentity: "-"`), so access would break on every build. It stays for when there is a real signing identity.
- **Tool allowlist limit:** `claude` matches `Bash(gh pr diff:*)` and the other `gh` patterns by prefix; the list only contains `gh` subcommands without a file-write flag, but a future `gh` version that adds such a flag would reopen it.

## Known limitations

- **`gh … <URL>` and `-R host/…` without a lock.** `Bash(gh pr view:*)` and the other `gh` patterns match by prefix, so Rust cannot stop `claude` from passing `gh` a URL from another host or `-R host/org/repo`; `gh` makes the request (POST included) to that host, and a prompt injected by PR content could use it to exfiltrate what the run read. There is no environment variable that restricts `gh` to `github.com` (`GH_HOST` only picks the default host, it does not block full URLs). Partial mitigation: the run starts in an empty folder or a git project, `Read` of `~/.ssh`, `~/.aws`, `~/.config`, `~/.claude`, `~/.gnupg`, `~/.kube`, `~/.docker`, `~/Library` and `~/AppData` is denied, and `WebFetch`/`WebSearch` are out. Accepted residual risk: what is still readable (for example, the text of the PRs and cards that the run itself fetches). The default skill does not need URLs, but that depends on the skill's prompt and is not enforced.
- No code signing (macOS and Windows). On macOS the bundle uses an ad-hoc signature (`signingIdentity: "-"`), which does not replace a Developer ID; the updater signature (minisign) only proves the package came from the release job. The updater was not run end to end against a real release yet: the flow was checked by Rust tests with local servers and by Vitest.
- The app's CSP (`src-tauri/tauri.conf.json`) only allows `self` and IPC (all HTTP goes through `plugin-http`, with an allowlist in the capability). It was not validated by running the Tauri app.
- The behavior on Windows (popover position, hiding on focus loss, `terminal_run` with `cwd`, removal of the `\\?\` prefix, `taskkill`) was not validated on a Windows machine; CI only compiles and runs tests.
- Skill runs were never executed with the real `claude` at this stage: the `stream-json` format (including `mcp_servers[].status` in the `init`) follows the documentation and the fixtures in `domain/skills/stream-fixtures.ts`. A `claude` installed through npm depends on `node` in the `PATH`, which an app opened from Finder may not have; the native installer (`~/.local/bin/claude`) does not have this problem.
- The notification at the end of the run, the sending through the plugin and `RunEvent::Exit` were not exercised in the real Tauri app (only by fakes and Rust tests of the registry). On macOS the notification depends on the packaged app having system permission.
- Nothing was validated against real GitHub, Microsoft Graph and Anthropic: the response formats follow the documentation and the test fixtures. The "See all" link of the reviewed ones uses `OR` with parentheses in the GitHub search.
- `terminal_run` with `cwd` and `/mcp` was only validated by policy tests; the macOS Terminal AppleScript was not executed.
- Demo mode runs only in the browser; it does not exercise the Rust commands.
- The tray usage icon was only validated as an image (PNGs in `docs/tray-preview/`) and by renderer tests; `tray_set_usage` did not run in the real Tauri app, and the look in the macOS menu bar and the Windows tray was not checked.
