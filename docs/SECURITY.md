# ClawdMeter security

This document gathers the app's security model: what Rust lets the webview do, the process and tool policy for skills, the capabilities, the CSP and the known open items. For the product overview, see the [README](../README.md); for the architecture, [ARCHITECTURE.md](ARCHITECTURE.md).

Summary: everything runs locally; the app only talks to `platform.claude.com` (Claude OAuth token endpoint), `api.anthropic.com`, `api.github.com` (plus GitHub's release-asset storage for update downloads) and `graph.microsoft.com`, and opens `claude.ai` in the browser for the Claude sign-in. Each Claude account has its own OAuth sign-in done by the app (see [Known deviation from Anthropic policy](#known-deviation-from-anthropic-policy)); its tokens are kept in the OS keyring, refreshed in Rust and never handed to the webview.

## Rust commands (`src-tauri/src/commands`)

Each command has its own permission (`allow-<name>` in `capabilities/default.json`, declared in `build.rs`). Errors reach TS as `{ kind, message }` (`rate_limited` adds `retryAfterSecs`, see below) and become `ConnectionProblemError` (`claude_signin_required`) or `PlatformCommandError`. In Rust the type is `CommandError` (`thiserror`, with `From` for `io`, `keyring`, `reqwest`, `tauri` and `url`) and the `kind` is one of: `keychain`, `claude_signin_required`, `program_not_allowed`, `program_not_found`, `invalid_argument`, `policy`, `spawn_failed`, `too_many_processes`, `timeout`, `state_mismatch`, `provider_error`, `cancelled`, `http`, `rate_limited`, `tray`, `io`. A Keychain or Credential Manager prompt the user denies also reaches TS as `keychain`; Rust keeps it apart internally (`ErrorKind::KeychainDenied`, serialized as `keychain`) only so the legacy secrets migration can settle on it (N6) and the [keyring cache](#keyring-cache) can pause reads after it (on macOS it is told apart by the Security framework status code, see there). Commands that block (`process_run`, `oauth_loopback_wait`, `process_kill`, `process_is_alive`, `secret_*`, `notification_permission_state`, `notification_permission_request`, `launch_at_login_*`, `session_usage`) are `async fn` and run the work in `spawn_blocking`, without tying up a runtime worker; the `claude_*` commands are `async fn` too and run their keyring access, socket bind and loopback wait through the same `run_blocking` (`claude_oauth_cancel` only touches memory).

## Keyring cache

Every access to the app's keyring service (`com.mottu.clawdmeter`) goes through one in-memory cache in Rust: `secrets::app_store()` returns a `CachedStore` over the keyring, and `secret_get/set/delete`, the `claude_*` commands (`claude_account_status`, `claude_oauth_complete`, `claude_account_remove`, and `claude_usage_fetch` with its token refresh) and the writes of the legacy secrets migration all use it. Without it, the usage poll, the GitHub and Microsoft calls and every status check read the Keychain again, and macOS showed the "wants to use your confidential information" prompt over and over to anyone who clicked **Allow** instead of **Always Allow**.

- **When it reads.** The first read of a key in the process reads the item once (the main entry plus its slices) and keeps the reassembled value; an absent item is kept as absent too, so a missing token is not looked up on every poll. The cache works on the logical key, never on the slices, and it also remembers how many slices are stored, so later writes and deletes clean the old slices without reading the item again. The only other read is the reread before a Claude refresh token is spent (see [Two app instances](#two-app-instances)).
- **When it does not read again.** Later reads of that key come from memory. A save writes to the keyring and updates the cache only when the write succeeds; a save of the value the cache already holds (same value, same slice count) does not touch the keyring at all. A delete removes the item and records the key as absent. A failed write or delete leaves the cache as it was. If the new value was written but removing the old slices failed, the cache keeps the new value and a later save or delete **in the same run** removes those slices. After a restart the slice count comes from the item's header, so slices beyond it (left by that failure, or by an older and longer value whose cleanup failed) stay in the keyring as orphans, even after a logout; the app never lists the service to find them (this predates the cache). Reads of the same key that arrive together wait for a single keyring read (one lock per key; other keys are not held up). The cache lock is never held across an `await`: the work runs inside `run_blocking`. The per-account lock of the Claude commands is unchanged.
- **Saves and deletes can prompt too (macOS).** The "at most one prompt per item per run" below holds for reads only. `keyring` saves through `set_generic_password`, which looks the item up (reading its data) before updating it, and deletes through the same lookup followed by the delete, so each save or delete of an item can show the prompt again after **Allow**. A save or delete of a key that was not read yet in this run also reads the main entry first to learn how many old slices to remove: one more possible prompt. This read is kept on purpose: skipping it would leave the slices of an older, longer value behind. How often this happens: the Claude refresh saves the account item at every renewal (Claude access tokens last a few hours, so about once every few hours per account, plus the reread before it), and the webview saves `microsoft.refresh-token` at every Microsoft renewal (about once an hour). When the user denies the lookup inside a save, `set_generic_password` falls back to adding a new item, and the Keychain answers `errSecDuplicateItem` (-25299) because the item exists; Rust treats that status on a save as a denial (`KeychainDenied`), never as a plain failure to retry.
- **A denied prompt.** On macOS a denial is recognized by the Security framework status code inside the `keyring` error (`security_framework::base::Error::code()`, never its text): -128 (`userCanceled`), -25293 (`errSecAuthFailed`, what **Deny** usually returns) and -25308 (`errSecInteractionNotAllowed`), plus -25299 on a save as above. On Windows the error text is still matched, as before. `NoStorageAccess` (on macOS: keychain not available, read-only or missing; on Windows: no logon session) is a configuration problem, not a denial: it is a plain `keychain` error, so it no longer pauses reads nor settles the legacy migration (N6), which then retries on the next launch. A denial read from the keyring is kept for 30 minutes (`KEYCHAIN_DENIAL_PAUSE`, well above the 5-minute usage poll): reads of that key during this time, the reread before a refresh included, return the same `keychain` error without touching the keyring, and the first read after it asks again. Saves and deletes are not paused, so saving a token or signing in again still reaches the keyring. Other failures (a transient `keychain` error, `io`) are not kept, and the next read tries again.
- **Changes made outside the app.** The cache lasts as long as the process. If an item is changed or deleted in Keychain Access (or Credential Manager) while the app runs, the app keeps using its copy until it restarts, except for the Claude reread below.
- <a id="two-app-instances"></a>**Two app instances.** `tauri-plugin-single-instance` (the first plugin registered in `lib.rs`) keeps one process per app identifier `com.mottu.clawdmeter` in each user session: a second launch (another copy of the `.app`, `open -n`, the dev build, launch at login plus a manual open) hands off to the running one, which opens the popover and logs `second-instance`, and then exits before the app `setup`, so it never reads the keyring. On macOS the lock is the Unix socket `/tmp/com_mottu_clawdmeter_si.sock` (a stale one left by a crash is removed by the next launch); on Windows a named mutex plus a hidden window that receives `WM_COPYDATA`. The arguments and working directory the second launch sends are ignored. Because the installed app and `yarn tauri dev` share the identifier, they no longer run side by side. What is left: any process of the same user can connect to the socket and open the popover (nothing else), another local account that already holds that socket path can keep ClawdMeter from starting, and if the plugin cannot reach or create the lock for another reason (for example a permission error on the socket) it starts normally, so two processes are still possible in that corner. For that case, and for two sessions of the same user on Windows, the reread below stays. Two instances share the keyring service `com.mottu.clawdmeter`. Each process has its own cache and does not see what the other writes. Before spending a Claude refresh token (`claude_usage_fetch`, when the token is within 5 minutes of expiry, or after a 401), Rust drops its cached copy of that account and reads the item again (`SecretStore::get_fresh`, about once every few hours per account). It then works with what it read: if the other instance already renewed, it uses those tokens and does not spend the old refresh token (Anthropic rotates it, and spending a rotated one would end in `invalid_grant` and a new sign-in); after a 401, tokens renewed elsewhere are retried before any refresh; an account the other instance marked `rejected` answers `claude_signin_required`. This narrows the race but does not close it: two instances that refresh at the same moment can still spend the same refresh token, because the per-account lock exists only inside one process. `microsoft.refresh-token` is renewed by the webview, which has no such reread, so two instances can still spend the same Microsoft refresh token. A save of the value already in a process's cache is skipped even if the other instance changed the item in the meantime.
- **What it holds.** The values stay only in the memory of the Rust process and are returned only where they were before: `secret_get` still refuses the `claude.account.*` keys with `policy`, and no command returns a Claude token. The `Debug` of the cache shows only key names and whether a value is present. The memory is not zeroed when a value is replaced (there is no `zeroize` dependency). Only the cache implements `SecretStore` in the app build: the plain keyring backend implements it only in tests, so production code cannot pass the uncached keyring where a `SecretStore` is expected.
- **The macOS prompt with an ad hoc signature.** The Keychain ties **Always Allow** to the app's code signature. The bundle has only an ad hoc signature (see [Known limitations](#known-limitations)), which changes with every build, so after each update macOS asks again, once per item (`github.token`, `microsoft.refresh-token` and each `claude.account.<accountId>`). With the cache, **Allow** covers the reads of the rest of the run (at most one read prompt per item per run, plus the Claude reread before each refresh), while saves and deletes can still prompt as described above; **Always Allow** lasts until the next build. Only a stable signing identity (Developer ID) would keep **Always Allow** across updates.

## Claude accounts (own OAuth sign-in)

Permissions (each `allow-<name>` in `capabilities/default.json`, declared in `build.rs`, TOML generated in `permissions/autogenerated/`). Arguments and results are camelCase JSON.

| Permission | Command | Arguments | Returns | Error kinds |
|---|---|---|---|---|
| `allow-claude-oauth-begin` | `claude_oauth_begin` | `{ clientId }` | `{ loginId, authorizeUrl, state, redirectUri, manualAuthorizeUrl }` | `invalid_argument`, `too_many_processes`, `io` |
| `allow-claude-oauth-complete` | `claude_oauth_complete` | `{ loginId, accountId, code?, timeoutMs? }` | `{ expiresAt, email }` (`expiresAt` in ms or `null`, `email` or `null`) | `invalid_argument`, `state_mismatch`, `timeout`, `cancelled`, `provider_error`, `rate_limited`, `http`, `keychain`, `io` |
| `allow-claude-oauth-cancel` | `claude_oauth_cancel` | `{ loginId }` | nothing | none (an unknown id is ignored) |
| `allow-claude-account-status` | `claude_account_status` | `{ accountId }` | `{ signedIn, expiresAt, needsLogin }` | `invalid_argument`, `keychain` |
| `allow-claude-account-remove` | `claude_account_remove` | `{ accountId }` | nothing | `invalid_argument`, `keychain` |
| `allow-claude-usage-fetch` | `claude_usage_fetch` | `{ accountId, clientId }` (`clientId` is only the fallback for tokens saved without one) | the usage JSON of `/api/oauth/usage`, unchanged | `invalid_argument`, `claude_signin_required`, `rate_limited`, `http`, `timeout`, `keychain`, `io` |

`allow-claude-usage-fetch` keeps its name; the command now takes arguments.

- **Sign-in start.** `claude_oauth_begin` validates `clientId` as a UUID (8-4-4-4-12 hex digits), draws the PKCE verifier (32 bytes), the `state` (32 bytes) and the `loginId` (16 bytes) from the OS random source (`getrandom`, base64url without padding) and opens a loopback listener through the `oauth_loopback` internals (bound to `127.0.0.1`, sharing the limit of 2 open listeners with the Microsoft sign-in). `authorizeUrl` sends `redirect_uri` to `http://localhost:<port>/callback`; `manualAuthorizeUrl` carries the same `state` and challenge with `redirect_uri=https://platform.claude.com/oauth/code/callback`, for the paste fallback. Both go to `https://claude.ai/oauth/authorize` with `code=true`, `client_id`, `response_type=code`, `redirect_uri`, `scope=user:profile user:inference`, `code_challenge`, `code_challenge_method=S256` and `state`. The verifier never leaves Rust. At most 2 sign-ins wait at once (`too_many_processes`), each kept in memory for 605 s.
- **Sign-in completion.** Without `code`, `claude_oauth_complete` waits for the browser on the loopback listener (a wrong or missing `state` gets 400 and the wait goes on; `timeoutMs` defaults to 2 min and is capped at 10 min; a second wait on the same sign-in is refused) and exchanges with the loopback `redirect_uri`. With `code` it expects the `code#state` that the code page shows (trimmed, at most 4096 bytes, `state` required and compared in constant time, as in ClaudeUsageBar's `submitOAuthCode`), closes the loopback listener and exchanges with the code page `redirect_uri`; a paste that fails this check keeps the sign-in pending, and a paste during a loopback wait takes the sign-in over (the wait ends with `cancelled`). The exchange is a JSON `POST https://platform.claude.com/v1/oauth/token` (`grant_type=authorization_code`, `code`, `state`, `client_id`, `redirect_uri`, `code_verifier`; 15 s timeout, answer up to 64 KiB, redirects not followed) and consumes the sign-in whatever the outcome. A refusal (4xx other than 408 and 429) gives `provider_error` with only the OAuth `error` code in the message, never the body; 429 gives `rate_limited`; anything else `http`. The tokens go to the keyring, and the e-mail is read from `GET https://api.anthropic.com/api/oauth/profile` (`account.email`; any failure gives `email: null`, never an error). `claude_oauth_cancel` closes the listener and forgets the sign-in, and can be called again.
- **Storage.** Keyring service `com.mottu.clawdmeter`, key `claude.account.<accountId>`, value JSON `{ accessToken, refreshToken, expiresAt, scopes, clientId }` (`expiresAt` in ms or `null` when unknown; `clientId` is the OAuth client of the sign-in that issued the tokens; `rejected: true` is added when the account must sign in again). Items saved before `clientId` existed are still read: they refresh with the `clientId` of `claude_usage_fetch` and, once that refresh succeeds, keep it. Values are sliced like the other secrets above 1200 bytes. The key is not in `ALLOWED_SECRET_KEYS`, so `secret_get/set/delete` refuse it with `policy` (Rust test); only the `claude_*` commands read and write it. `accountId` must match `[A-Za-z0-9_-]{1,64}` before any key is built, so it cannot name another key or a slice (`#`). No command returns a token, the `Debug` of the token type hides them and nothing about them is logged. An unreadable value counts as no tokens. `claude_account_remove` only deletes the local item (no remote revocation).
- **Status.** `claude_account_status` returns `signedIn` (tokens stored), `expiresAt` and `needsLogin`: true without tokens, when the token expired and there is no refresh token, or when the account is marked `rejected`. After the first read of the account it is answered from the [keyring cache](#keyring-cache), without touching the keyring.
- **Refresh and usage.** `claude_usage_fetch` validates both ids and holds a per-account lock from reading the tokens to saving them (`complete` and `remove` take the same lock), so two fetches of one app instance never spend the same refresh token and a fetch cannot write back tokens of a removed or re-signed account. Before each refresh it rereads the account item from the keyring and refreshes with what it read (see [Two app instances](#two-app-instances)). With 5 minutes or less left and a refresh token, it posts `grant_type=refresh_token` with `refresh_token`, the stored `clientId` (the `clientId` argument only when the item has none, so changing the client id in Settings does not break accounts already signed in) and the stored `scope`, and saves the rotated tokens before using them. A missing `refresh_token` in the answer keeps the previous one; a missing `expires_in` leaves `expiresAt` as `null` (it is never inherited from the previous token), and an expired token is then caught by the 401 path. A 401 on usage triggers one refresh and one retry. No tokens, an expired token without a refresh token, a 401 after the renewal, or a refresh refused with the OAuth `error` code `invalid_grant` or `invalid_client` (read from the JSON body of a 4xx) give `claude_signin_required`; the tokens are not deleted, only marked `rejected`, and later fetches answer `claude_signin_required` without calling Anthropic until a new sign-in replaces them. Any other refresh failure is transient and never marks the account: network, 5xx, 408, 429 and every other 4xx (a WAF 403 with HTML, 404, 405, 415, `invalid_request`, `invalid_scope`, `unauthorized_client`, an Anthropic `authentication_error`). With a token that has not expired yet the fetch falls back to that token; with an expired token the error is returned (`http`, or `rate_limited` for 429).
- **Saving rotated tokens.** If the keyring write after a refresh fails with `keychain`, Rust waits 200 ms and tries once more. If the retry also fails, the fetch ends with that `keychain` error and the new access token is not used for the request. This is a deliberate choice: returning usage while the rotated refresh token exists only in memory would hide the failure, and Anthropic may already have spent the stored refresh token, so the next refresh can be refused with `invalid_grant` and the account then asks for a new sign-in. What the keyring then holds depends on where the save failed. If writing the new value failed, the keyring and the cache keep the previous tokens (not marked `rejected`), so the old access token is still used while it lasts. If the new value was written and only the removal of old slices failed, the keyring and the cache already hold the new tokens even though this fetch returns the error, and the next fetch uses them. Other save errors (`io`, `invalid_argument`, a denied keychain prompt, `errSecDuplicateItem` on macOS included) are not retried, so a denial is not followed by a second prompt.

## Capabilities and CSP

Each command has its own permission (`allow-<name>` in `src-tauri/capabilities/default.json`, declared in `build.rs`). The plugin-fs scopes (Claude Code sessions, ClaudeUsageBar history, app config folder) and the plugin-http allowlist are checked by `tools/capabilities.spec.ts`. The CSP in `src-tauri/tauri.conf.json` only allows `self` and IPC. Details and limits in Security open items and Known limitations below and in [ARCHITECTURE.md](ARCHITECTURE.md).

## Launch at login

- **Surface.** Three app commands, `launch_at_login_status`, `launch_at_login_enable` and `launch_at_login_disable` (`commands/launch_at_login.rs`), each with its own permission (`allow-launch-at-login-status`, `allow-launch-at-login-enable`, `allow-launch-at-login-disable`). No Tauri plugin and no `autostart:` permission: `tools/capabilities.spec.ts` locks the exact list of `launch-at-login` permissions and fails if any `autostart:` permission appears in a capability file or the plugin comes back to `Cargo.toml`/`package.json`. The commands take no arguments, so the webview can only read the state and turn it on or off.
- **What it writes.** macOS: `~/Library/LaunchAgents/ClawdMeter.plist` with the canonical path of the running executable, no arguments, `RunAtLoad` and `AssociatedBundleIdentifiers` = `com.mottu.clawdmeter` (read from the Tauri config). Windows: the `ClawdMeter` value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` with the quoted `.exe` path (`WindowsEnableMode::CurrentUser`); `HKLM` is never written, so a switch turned on by an elevated app can still be turned off without elevation. Other systems: nothing is written. Nothing is registered until the user turns the switch on.
- **Path guard (macOS).** `enable` refuses with `policy` when the canonical executable is under `/Volumes/` (the mounted `.dmg`) or contains `/AppTranslocation/` (Gatekeeper's temporary copy), so the agent never points at a path that disappears; the message asks to move the app to `/Applications` and does not include the path. Other `auto-launch` errors become `io` with a generic message (no path); I/O errors keep the system message.
- **Rewrite on launch.** At startup of a release build, when the status is on, Rust calls `enable` again so the agent follows the `.app` after a move (skipped when the plist already points at the same executable and bundle identifier). A failure is logged to `popover.log` and does not stop the startup; the location guard also applies here, so a copy opened from the `.dmg` does not overwrite a good path.
- **Dependency.** `auto-launch` 0.6.0 (MIT), only for macOS and Windows, which on macOS also pulls `smappservice-rs` 0.1.3 (MIT), `objc2-service-management`/`objc2-security` 0.3.2 (Zlib/Apache-2.0/MIT), `os_info` 3.15.0 (MIT) and `dirs` 6.0.0 next to the `dirs` 7 already in the tree (a duplicate that `deny.toml` only warns about), and on Windows `windows-registry` 0.6.1 (already in the tree). `cargo deny check` passes without touching `deny.toml`, and `cargo audit` finds no vulnerability and the same 5 allowed warnings as `main`.
- **Limits.** On macOS the status only checks that the plist exists: an item turned off in System Settings > General > Login Items, or a plist whose executable is gone, still reads as on. Deleting the app with the switch on leaves the plist (or the `Run` value) behind; the README Uninstall section says how to remove it. Any script running in the webview can turn launch at login on or off, the same trust level as the rest of the IPC (the CSP only allows `self`).

## Skills policy (`claude -p`)

- **Tools: exact allowlist.** `--allowedTools` only accepts entries identical to those in `ALLOWED_CLAUDE_TOOLS` (`process_policy.rs`, mirrored in `skill-definition.ts` by a test that reads the Rust file): `Read(./**)`, `Bash(gh pr list|view|checks|diff:*)` and `Bash(gh search prs:*)`. The two Jira MCP tools (`mcp__plugin_atlassian_atlassian__searchJiraIssuesUsingJql` and `getJiraIssue`) left the list in round 4, because no MCP server loads any more (see below). `Bash` without a pattern, `Bash(*)`, `Bash(git:*)`, `Bash(gh:*)`, `Read` without a scope, `Write`, `Edit`, any `*` and any other tool are blocked in Rust; in TS the run fails before opening the process with "Skill … uses a tool that is not allowed: …". `Grep` and `Glob` are not in the list: `claude` runs them without a rule inside the run's `cwd` and, outside it, `dontAsk` denies them; an old `skills.json` with `Grep`/`Glob` fails with "Update skills.json". The helper scripts of `/acabativa` (`bash`/`python`) are left out on purpose.
- **`skills.json` migration (round 2).** `Bash(git diff:*)`, `Bash(git log:*)` and `Bash(git status:*)` left the list because `claude` matches the pattern by prefix and the subcommand accepts write flags (`git diff --output=$HOME/.zshrc` writes an arbitrary file); swap for `Bash(gh pr diff:*)` or remove. `Read` became `Read(./**)` (a read rule relative to the run's directory, Claude Code permission rule syntax, not confirmed by running `claude`). A `skills.json` with the old names is still read, but the run fails before opening the process with the message "Skill … uses a tool that is not allowed: …. Update skills.json …". With a null `cwd` the run starts in the app's empty `skill-cwd` folder (round 3), so `Read(./**)` covers only it; a skill that needs to read a project sets its `cwd` in `skills.json`.
- **Flags injected by Rust (round 4).** After validating the argv coming from the webview, `process_spawn` always appends to the end of any `claude -p`, in this order: `--setting-sources "" --settings <app_cache_dir>/claude-settings.json --strict-mcp-config --permission-mode dontAsk --disallowedTools <deny list>` (`prepare_invocation` in `process_policy.rs`; a `claude -p` without the settings file is refused with `policy`). TS does not pass these flags and Rust blocks them if they come from the webview, including in the `--flag=value` form (`--settings`, `--setting-sources`, `--permission-mode`, `--dangerously-skip-permissions`, `--add-dir`, `--mcp-config`, `--strict-mcp-config`, `--disallowedTools`/`--disallowed-tools`).
  - **No user settings (N1).** `--setting-sources ""` loads no `user`, `project` or `local` settings file, so `~/.claude/settings.json` (its `permissions.allow`, hooks, `defaultMode`) no longer applies to skill runs. Checked against the local `claude` 2.1.318: `--help` lists `--setting-sources <sources>` ("Comma-separated list of setting sources to load (user, project, local)"), `--settings <file-or-json>` and `--strict-mcp-config` ("Only use MCP servers from --mcp-config, ignoring all other MCP configurations"); the flag parser in the binary returns an empty list for `""` (`if(e==="")return[]`) and only throws `Invalid setting source` for an unknown name. Managed (enterprise) settings still apply, as in any `claude` run. Not confirmed by running `claude -p`.
  - **App-owned settings file.** Rust rewrites `app_cache_dir()/claude-settings.json` before every spawn (temp file + rename, so a symlink planted there is replaced, not followed): `permissions.allow` = `ALLOWED_CLAUDE_TOOLS`, `permissions.deny` = the deny list, `defaultMode: dontAsk`, `disableBypassPermissionsMode: disable`, `disableAllHooks: true`, `enableAllProjectMcpServers: false`. `app_cache_dir()` is outside every webview `fs` scope (a Rust test checks that the capability never names `$APPCACHE`); `$APPDATA` was not used because on macOS it is the same folder as `$APPCONFIG`, which the webview can write. Since the file's `allow` is the whole allowlist, a skill that passes a narrower `--allowedTools` can still use the other allowlisted tools; the ceiling is the allowlist.
  - **No MCP servers (N1).** `--strict-mcp-config` without `--mcp-config` starts no MCP server: not the user's, not the plugins', not a `.mcp.json` in the run's folder. **The Jira integration of skills (the cards `/acabativa` reads) is off** until the app ships its own `mcp-config` with only the Atlassian server; the skill still runs, without the Jira part.
  - **Project folders only (N2).** An explicit `cwd` must be a git project (a `.git` folder or file) inside the user's folder and outside `~/Library`, `~/.config`, `~/.kube`, `~/.docker`, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.claude`, `~/AppData` and the app's config, data, cache and log folders (compared by whole path components, ignoring case on macOS and Windows). Without `cwd` the run still starts in the empty `skill-cwd`. `terminal_run` keeps the earlier rule (home subfolder, not `~/.claude` or the app config), because `claude --resume` must reopen the folder where the session ran.
  - **Reading of sensitive paths denied (rounds 3 and 4).** `--disallowedTools` (and the settings file's `deny`) carry `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, `WebFetch`, `WebSearch`, `Read(~/.ssh/**)`, `Read(~/.aws/**)`, `Read(~/.config/**)`, `Read(~/.claude/**)`, `Read(~/.gnupg/**)`, `Read(~/.kube/**)`, `Read(~/.docker/**)`, `Read(~/Library/**)` and `Read(~/AppData/**)`. Not confirmed by running `claude`: `--help` only lists the flag and the `Bash(git *)` format, not the `Read(~/…)` rule syntax; it follows the Claude Code permissions documentation (`~/` is the user's folder; a `Read` rule also applies to `Grep` and `Glob`, on a best-effort basis). That is why there are no separate `Grep(...)`/`Glob(...)` rules. Side effect: a skill support file that lives in `~/.claude` and is read through the `Read` tool is also denied.
  - **`gh` variable.** Rust sets `GH_PROMPT_DISABLED=1` in the children's environment, so `gh` never waits for a prompt.
  - **`Bash` outside `--disallowedTools`.** The review asked for `Bash` in the denied list, but deny beats allow in Claude Code: a denied `Bash` would cancel `Bash(gh pr …:*)` and the skill would be left without `gh`. Only the four write tools go in. Residual risk: a skill with `allowed-tools: Bash` in its frontmatter can widen Bash beyond the `gh` patterns.
  - **`process_spawn` only accepts `claude -p` (round 3).** `claude /login` and `claude --resume <uuid>` used to be accepted without the hardening flags; now they are refused (`claude arguments not allowed`) and only run in the interactive terminal.
  - `terminal_run` with `claude` only accepts `/login`, `/mcp` and `--resume <uuid>` (never `-p`), so there is no `claude -p` path that escapes these flags.

## Updates

- **Signature.** Every updater artifact (`.app.tar.gz`, `.msi`, `.exe`) is signed in the release job with the minisign key in the `TAURI_SIGNING_PRIVATE_KEY` secret. The app carries only the public key (`plugins.updater.pubkey` in `tauri.conf.json`) and `Update::install` refuses a package whose signature does not match. `requireSignedVersion: true` (and `restore_update`, which forces it) also requires the version in the signature's trusted comment to equal the version in `latest.json`, so a changed `latest.json` cannot pair a new version number with an older signed package. The private key lives only on the maintainer's machine (`~/.tauri/clawdmeter-updater.key`) and in the Actions secret, never in the repository.
- **Token.** The GitHub token is the one of the GitHub connection (gh CLI, device flow or PAT). It is resolved by `GitHubTokenResolver` like for PRs (so it still crosses the IPC, the debt below) and handed to the `updater_check`/`updater_install` commands; every update request is made in Rust, none through the webview `plugin-http`, so the http capability did not change.
- **No token in redirects.** The asset API answers with a 302 to a signed URL on `release-assets.githubusercontent.com` (or `objects.githubusercontent.com`). The client has `redirect::Policy::none()` and follows each hop itself: `Authorization` is only sent to `api.github.com`, the storage host gets the request without it, and any other host or a non-https URL ends the download with `policy` before connecting (Rust tests with local servers check the header on each side). The package URL itself must be an `api.github.com` asset URL: `updater_check` rewrites every `latest.json` entry to `/repos/<repo>/releases/assets/<id>` of an asset of the same release and drops entries that do not match.
- **Permissions.** The webview gets `allow-updater-check`, `allow-updater-install` and `allow-updater-restart` only; no `updater:*` permission of the plugin, so the plugin's own JS commands are unreachable (`tools/capabilities.spec.ts`).
- **Limits.** Release JSON 1 MiB, `latest.json` 64 KiB, package 300 MiB, at most 3 redirects, 20 s timeout for the check and 15 min for the download. The check runs at most every 6 h and stops while GitHub reports a rate limit.

## Security open items (Rust review)

- **Debt: GitHub and Graph tokens still cross the IPC.** The Claude tokens never leave Rust (`claude_*` commands), but `secret_get` still returns `github.token` and `microsoft.refresh-token` to the webview, which makes the calls to GitHub and Microsoft Graph through `tauri-plugin-http` and passes the GitHub token back to the `updater_*` commands. Moving those calls to Rust (as was done for usage) is the next step; until then `secret_*` only accepts these two keys.
- **Tool allowlist limit:** `claude` matches `Bash(gh pr diff:*)` and the other `gh` patterns by prefix; the list only contains `gh` subcommands without a file-write flag, but a future `gh` version that adds such a flag would reopen it.

## Known deviation from Anthropic policy

ClawdMeter runs its own Claude.ai OAuth sign-in and stores the resulting tokens, which [Anthropic's legal and compliance page](https://code.claude.com/docs/en/legal-and-compliance) ("Authentication and credential use") does not allow: third-party developers must not offer Claude.ai login in their applications nor collect, store or route Claude.ai credentials or session tokens.
The user accepted this risk for personal use, knowing Anthropic may enforce it against the account without notice.
The OAuth client id defaults to the one ClaudeUsageBar uses (`9d1c250a-e61b-44d9-88ed-5944d1962f5e`, apparently Claude Code's public client) and can be replaced in Settings (**Use default client ID: No**); Rust receives it as `clientId` and validates it as a UUID.
This replaced the earlier source, which read Claude Code's own login (macOS Keychain item `Claude Code-credentials` through `/usr/bin/security`, or `~/.claude/.credentials.json`); that code, the `claude_credentials_status` command with its `allow-claude-credentials-status` permission, and the open item S3 are gone.

## Known limitations

- **`gh … <URL>` and `-R host/…` without a lock.** `Bash(gh pr view:*)` and the other `gh` patterns match by prefix, so Rust cannot stop `claude` from passing `gh` a URL from another host or `-R host/org/repo`; `gh` makes the request (POST included) to that host, and a prompt injected by PR content could use it to exfiltrate what the run read. There is no environment variable that restricts `gh` to `github.com` (`GH_HOST` only picks the default host, it does not block full URLs). Partial mitigation: the run starts in an empty folder or a git project, `Read` of `~/.ssh`, `~/.aws`, `~/.config`, `~/.claude`, `~/.gnupg`, `~/.kube`, `~/.docker`, `~/Library` and `~/AppData` is denied, and `WebFetch`/`WebSearch` are out. Accepted residual risk: what is still readable (for example, the text of the PRs and cards that the run itself fetches). The default skill does not need URLs, but that depends on the skill's prompt and is not enforced.
- No code signing (macOS and Windows). On macOS the bundle uses an ad-hoc signature (`signingIdentity: "-"`), which does not replace a Developer ID; the updater signature (minisign) only proves the package came from the release job. The updater was not run end to end against a real release yet: the flow was checked by Rust tests with local servers and by Vitest.
- The app's CSP (`src-tauri/tauri.conf.json`) only allows `self` and IPC (all HTTP goes through `plugin-http`, with an allowlist in the capability). It was not validated by running the Tauri app.
- The behavior on Windows (popover position, hiding on focus loss, `terminal_run` with `cwd`, removal of the `\\?\` prefix, `taskkill`) was not validated on a Windows machine; CI only compiles and runs tests.
- Skill runs were never executed with the real `claude` at this stage: the `stream-json` format (including `mcp_servers[].status` in the `init`) follows the documentation and the fixtures in `domain/skills/stream-fixtures.ts`. A `claude` installed through npm depends on `node` in the `PATH`, which an app opened from Finder may not have; the native installer (`~/.local/bin/claude`) does not have this problem.
- The notification at the end of the run, the sending through the plugin and `RunEvent::Exit` were not exercised in the real Tauri app (only by fakes and Rust tests of the registry). On macOS the notification depends on the packaged app having system permission.
- Nothing was validated against real GitHub, Microsoft Graph and Anthropic: the response formats follow the documentation and the test fixtures. The Claude sign-in, token refresh and profile read were only exercised by Rust tests with local servers; endpoints, parameters and scopes mirror ClaudeUsageBar's `UsageService.swift`. The "See all" link of the reviewed ones uses `OR` with parentheses in the GitHub search.
- `terminal_run` with `cwd` and `/mcp` was only validated by policy tests; the macOS Terminal AppleScript was not executed.
- Demo mode runs only in the browser; it does not exercise the Rust commands.
- The tray usage icon was only validated as an image (PNGs in `docs/tray-preview/`) and by renderer tests; `tray_set_usage` did not run in the real Tauri app, and the look in the macOS menu bar and the Windows tray was not checked.
