# ClawdMeter security

This document gathers the app's security model: what Rust lets the webview do, the process and tool policy for skills, the capabilities, the CSP and the known open items. For the product overview, see the [README](../README.md); for the architecture, [ARCHITECTURE.md](ARCHITECTURE.md).

Summary: everything runs locally; the app only talks to `api.anthropic.com`, `api.github.com` and `graph.microsoft.com`; the Claude Code credential is read in read-only mode, never refreshed and never handed to the webview.

## Rust commands (`src-tauri/src/commands`)

Each command has its own permission (`allow-<name>` in `capabilities/default.json`, declared in `build.rs`). Errors reach TS as `{ kind, message }` (`rate_limited` adds `retryAfterSecs`, see below) and become `ConnectionProblemError` (`keychain_denied`, `claude_code_missing`, `claude_expired`) or `PlatformCommandError`. In Rust the type is `CommandError` (`thiserror`, with `From` for `io`, `keyring`, `reqwest`, `tauri` and `url`) and the `kind` is one of: `keychain_denied`, `keychain`, `claude_code_missing`, `claude_expired`, `credential_malformed`, `program_not_allowed`, `program_not_found`, `invalid_argument`, `policy`, `spawn_failed`, `too_many_processes`, `timeout`, `state_mismatch`, `provider_error`, `cancelled`, `http`, `rate_limited`, `tray`, `io`. Commands that block (`process_run`, `oauth_loopback_wait`, `process_kill`, `process_is_alive`, `secret_*`, `claude_*`, `notification_permission_state`) are `async fn` and run the work in `spawn_blocking`, without tying up a runtime worker.

| Module | Commands | Notes |
|---|---|---|
| `secrets` | `secret_get/set/delete` | `keyring` crate (Keychain / Credential Manager), service `com.mottu.clawdmeter`; only the keys in `ALLOWED_SECRET_KEYS` (`github.token`, `microsoft.refresh-token`, mirrored in `SECRET_KEYS` by a test), any other gives `policy`; secrets above 1200 bytes are sliced into `<key>`, `<key>#1`… (Credential Manager limits the blob to 2560 bytes) |
| `claude_credentials` | `claude_credentials_status`, `claude_usage_fetch` | reads the Claude Code credential (Keychain/file) and does the `GET https://api.anthropic.com/api/oauth/usage` (`anthropic-beta: oauth-2025-04-20`, 15 s timeout, response up to 256 KiB) with the `reqwest` of `tauri-plugin-http`; returns only `{ expiresAt, subscriptionType }` or the usage JSON. An expired credential or 401 gives `claude_expired`; 429 gives `{ kind: 'rate_limited', message, retryAfterSecs }`, with `retryAfterSecs` taken from the `Retry-After` header (seconds or HTTP date `IMF-fixdate`, converted to seconds from now, never negative) and `null` when the header is missing or invalid; the other statuses, 5xx included, follow `http`; a denied Keychain, `claude_code_missing` and `credential_malformed` keep their `kind`. The `http:default` allowlist no longer has `api.anthropic.com` |
| `process` | `process_run/spawn/kill/is_alive` | only `claude` and `gh`, with per-program validated arguments (`process_policy.rs`): `gh auth token [-h github.com]`; `claude -p <prompt> --output-format stream-json [--verbose] --max-budget-usd <n> [--allowedTools <list>]` (the list goes in a single comma-separated argument) and nothing else: `/login`, `/mcp` and `--resume <uuid>` do not go through `process_spawn`, only through `terminal_run`; no `--dangerously-skip-permissions`, `--permission-mode`, `--add-dir` and `--mcp-config`; an explicit `cwd` only the user's folder or subfolders; without `cwd`, `process_spawn` uses an empty app working directory, `app_cache_dir()/skill-cwd` (created if missing, outside `$APPCONFIG` and outside any webview `fs` scope, which a test checks in `capabilities/default.json`), and only the `gh` `process_run` falls back to the user's folder (on Windows the `\\?\` prefix of the canonical path is removed), never inside the app config directory (`app_config_dir()`, resolved by the `AppHandle`) nor `~/.claude`: on Windows the Tauri `fs` scope accepts dotted paths, so the webview could write `$APPCONFIG\.claude\settings.json` and run claude there; `process_run` only runs `gh` (`claude` only goes through `process_spawn`, which injects the hardening flags); a timeout ends the group; `kill` only for the app's children (an unknown or already ended pid is ignored); on app exit (`RunEvent::Exit`) children still alive are killed; at most 4 simultaneous processes (`too_many_processes`); `kill` of a pid that is already exiting is ignored, because the registry marks the pid as "exiting" under the same lock as `kill` before `wait()` does the reap (on Unix the wait uses `waitid(WNOWAIT)`, which leaves the zombie until the mark); the output captured in `process_run` is limited to 1 MiB per stream (with a `[output truncated]` mark) and each stream line to 4 MiB on stdout (`stream-json` carries one event per line, and the `result` can be large) and 64 KiB on stderr (with a `…[line truncated]` mark; TS recognizes the mark on a stdout line that starts with `{` and flags the run with the error "Output truncated: …" instead of the generic "ended without a result"; if an intermediate event is cut but the final `result` arrives intact, the run goes on as completed); `process-output` and `process-exit` events |
| `oauth_loopback` | `oauth_loopback_listen/wait/cancel` | validates `state`, timeout, local return page; a callback with a wrong or missing `state` gets 400 and the listener keeps waiting, only a provider error with a valid `state` ends it; each connection has a total of 5 s to deliver the header (in addition to 2 s per read), so a client that pings one byte at a time does not hold the listener (the worst delay for a cancel is this deadline, because accept is sequential); interrupted reads (`ErrorKind::Interrupted`) are retried, both here and in the `process_run` capture |
| `terminal` | `terminal_run` | `claude`/`gh` with the same per-program policy (`claude /login`, `/mcp`, `--resume <uuid>`, never `claude -p`; `gh auth login/refresh`) and arguments without shell metacharacters; accepts `cwd` (the run's folder, validated as in `process`, including the refusal of `app_config_dir()` and `~/.claude`, without quotes or backslash); without `cwd` it opens in the user's folder, except `claude --resume <uuid>`, which reopens in `app_cache_dir()/skill-cwd` because `claude` stores the session per directory and the run started there; the program goes by the resolved absolute path (the same `resolve_program` as `process`), inside single quotes like the `cwd` |
| `notification_permission` | `notification_permission_state` | `granted`, `denied`, `prompt` or `unknown` |
| `open_external` | `open_url`, `open_system_settings` | only `https` and known panes |

HTTP access to GitHub and Microsoft goes through `tauri-plugin-http` (avoids WebView CORS), with a URL allowlist in the capability.

## Capabilities and CSP

Each command has its own permission (`allow-<name>` in `src-tauri/capabilities/default.json`, declared in `build.rs`). The plugin-fs scopes (Claude Code sessions, ClaudeUsageBar history, app config folder) and the plugin-http allowlist are checked by `tools/capabilities.spec.ts`. The CSP in `src-tauri/tauri.conf.json` only allows `self` and IPC. Details and limits in Security open items and Known limitations below and in [ARCHITECTURE.md](ARCHITECTURE.md).

## Skills policy (`claude -p`)

- **Tools: exact allowlist.** `--allowedTools` only accepts entries identical to those in `ALLOWED_CLAUDE_TOOLS` (`process_policy.rs`, mirrored in `skill-definition.ts` by a test that reads the Rust file): `Read(./**)`, `Bash(gh pr list|view|checks|diff:*)`, `Bash(gh search prs:*)` and two read-only Jira MCP tools that `/acabativa` uses (`mcp__plugin_atlassian_atlassian__searchJiraIssuesUsingJql` and `getJiraIssue`). `Bash` without a pattern, `Bash(*)`, `Bash(git:*)`, `Bash(gh:*)`, `Read` without a scope, `Write`, `Edit`, any `*` and any other tool are blocked in Rust; in TS the run fails before opening the process with "Skill … uses a tool that is not allowed: …". `Grep` and `Glob` are not in the list: `claude` runs them without a rule inside the run's `cwd` and, outside it, `dontAsk` denies them; an old `skills.json` with `Grep`/`Glob` fails with "Update skills.json". The helper scripts of `/acabativa` (`bash`/`python`) are left out on purpose.
- **`skills.json` migration (round 2).** `Bash(git diff:*)`, `Bash(git log:*)` and `Bash(git status:*)` left the list because `claude` matches the pattern by prefix and the subcommand accepts write flags (`git diff --output=$HOME/.zshrc` writes an arbitrary file); swap for `Bash(gh pr diff:*)` or remove. `Read` became `Read(./**)` (a read rule relative to the run's directory, Claude Code permission rule syntax, not confirmed by running `claude`). A `skills.json` with the old names is still read, but the run fails before opening the process with the message "Skill … uses a tool that is not allowed: …. Update skills.json …". With a null `cwd` the run starts in the app's empty `skill-cwd` folder (round 3), so `Read(./**)` covers only it; a skill that needs to read a project sets its `cwd` in `skills.json`.
- **Flags injected by Rust (round 2).** After validating the argv coming from the webview, `process_spawn` always appends to the end of any `claude -p`: `--setting-sources user --permission-mode dontAsk --disallowedTools Write,Edit,MultiEdit,NotebookEdit,WebFetch,WebSearch,Read(~/.ssh/**),Read(~/.aws/**),Read(~/.config/gh/**),Read(~/.claude/**),Read(~/.gnupg/**)` (`prepare_invocation` in `process_policy.rs`, in that order). TS does not pass these flags and Rust blocks them if they come from the webview, including in the `--flag=value` form (`--settings`, `--setting-sources`, `--permission-mode`, `--dangerously-skip-permissions`, `--add-dir`, `--mcp-config`, `--strict-mcp-config`, `--disallowedTools`/`--disallowed-tools`). The names were checked against the local `claude --help` (2.1.318): `--setting-sources <sources>` (a list of `user`, `project`, `local`), `--disallowedTools, --disallowed-tools <tools...>` and `--permission-mode <mode>` with the options `acceptEdits`, `auto`, `bypassPermissions`, `manual`, `dontAsk` and `plan`. `--setting-sources user` still reads the user's `~/.claude/settings.json`, and a permissive `permissions.defaultMode` in it would apply to the run; that is why Rust pins `--permission-mode dontAsk` (denies everything not in `--allowedTools`) and denies `WebFetch` and `WebSearch`, which are not part of the allowlist. Effect: the project's `settings.json`/hooks/permissions (`<cwd>/.claude/`) and `settings.local.json` are not read, and the deny rules apply even if a skill's frontmatter brings a wider `allowed-tools`, since deny beats allow.
  - **Reading of sensitive paths denied (round 3).** `--disallowedTools` carries `Read(~/.ssh/**)`, `Read(~/.aws/**)`, `Read(~/.config/gh/**)`, `Read(~/.claude/**)` and `Read(~/.gnupg/**)`. Not confirmed by running `claude`: `--help` only lists the flag and the `Bash(git *)` format, not the `Read(~/…)` rule syntax; it follows the Claude Code permissions documentation (`~/` is the user's folder; a `Read` rule also applies to `Grep` and `Glob`, on a best-effort basis). That is why there are no separate `Grep(...)`/`Glob(...)` rules. Side effect: a skill support file that lives in `~/.claude` and is read through the `Read` tool is also denied.
  - **`gh` variable.** Rust sets `GH_PROMPT_DISABLED=1` in the children's environment, so `gh` never waits for a prompt.
  - **`Bash` outside `--disallowedTools`.** The review asked for `Bash` in the denied list, but deny beats allow in Claude Code: a denied `Bash` would cancel `Bash(gh pr …:*)` and the skill would be left without `gh`. Only the four write tools go in. Residual risk: a skill with `allowed-tools: Bash` in its frontmatter can widen Bash beyond the `gh` patterns.
  - **User MCPs load.** Rust does not inject `--strict-mcp-config`, so the user's and plugins' MCP servers load again; `--allowedTools` still restricts the MCP tools to the two Jira read ones (`searchJiraIssuesUsingJql` and `getJiraIssue`). `--mcp-config` and `--strict-mcp-config` coming from the webview remain blocked.
  - **`process_spawn` only accepts `claude -p` (round 3).** `claude /login` and `claude --resume <uuid>` used to be accepted without the hardening flags; now they are refused (`claude arguments not allowed`) and only run in the interactive terminal.
  - `terminal_run` with `claude` only accepts `/login`, `/mcp` and `--resume <uuid>` (never `-p`), so there is no `claude -p` path that escapes these flags.

## Security open items (Rust review)

- **Debt: GitHub and Graph tokens still cross the IPC.** The Claude token no longer leaves Rust (`claude_usage_fetch`), but `secret_get` still returns `github.token` and `microsoft.refresh-token` to the webview, which makes the calls to GitHub and Microsoft Graph through `tauri-plugin-http`. Moving those calls to Rust (as was done for usage) is the next step; until then `secret_*` only accepts these two keys.
- **Open item S3 (macOS): Keychain read via `/usr/bin/security`.** If the user picks "Always Allow", access is granted to the `security` binary, not to ClawdMeter, and any local process starts reading the Claude Code credential without a prompt. The fix is to use the native API (`security-framework`), which ties access to the app's signature; today the app is signed ad hoc (`signingIdentity: "-"`), so access would break on every build. It stays for when there is a real signing identity.
- **Tool allowlist limit:** `claude` matches `Bash(gh pr diff:*)` and the other `gh` patterns by prefix; the list only contains `gh` subcommands without a file-write flag, but a future `gh` version that adds such a flag would reopen it.

## Known limitations

- **`gh … <URL>` and `-R host/…` without a lock.** `Bash(gh pr view:*)` and the other `gh` patterns match by prefix, so Rust cannot stop `claude` from passing `gh` a URL from another host or `-R host/org/repo`; `gh` makes the request (POST included) to that host, and a prompt injected by PR content could use it to exfiltrate what the run read. There is no environment variable that restricts `gh` to `github.com` (`GH_HOST` only picks the default host, it does not block full URLs). Partial mitigation: the run starts in an empty folder, `Read` of `~/.ssh`, `~/.aws`, `~/.config/gh`, `~/.claude` and `~/.gnupg` is denied, and `WebFetch`/`WebSearch` are out. Accepted residual risk: what is still readable (for example, the text of the PRs and cards that the run itself fetches). The default skill does not need URLs, but that depends on the skill's prompt and is not enforced.
- No code signing (macOS and Windows) and no updater. On macOS the bundle uses an ad-hoc signature (`signingIdentity: "-"`), which does not replace a Developer ID.
- The app's CSP (`src-tauri/tauri.conf.json`) only allows `self` and IPC (all HTTP goes through `plugin-http`, with an allowlist in the capability). It was not validated by running the Tauri app.
- The behavior on Windows (popover position, hiding on focus loss, `terminal_run` with `cwd`, removal of the `\\?\` prefix, `taskkill`) was not validated on a Windows machine; CI only compiles and runs tests.
- Skill runs were never executed with the real `claude` at this stage: the `stream-json` format (including `mcp_servers[].status` in the `init`) follows the documentation and the fixtures in `domain/skills/stream-fixtures.ts`. A `claude` installed through npm depends on `node` in the `PATH`, which an app opened from Finder may not have; the native installer (`~/.local/bin/claude`) does not have this problem.
- The notification at the end of the run, the sending through the plugin and `RunEvent::Exit` were not exercised in the real Tauri app (only by fakes and Rust tests of the registry). On macOS the notification depends on the packaged app having system permission.
- Nothing was validated against real GitHub, Microsoft Graph and Anthropic: the response formats follow the documentation and the test fixtures. The "See all" link of the reviewed ones uses `OR` with parentheses in the GitHub search.
- `terminal_run` with `cwd` and `/mcp` was only validated by policy tests; the macOS Terminal AppleScript was not executed.
- Demo mode runs only in the browser; it does not exercise the Rust commands.
- The tray usage icon was only validated as an image (PNGs in `docs/tray-preview/`) and by renderer tests; `tray_set_usage` did not run in the real Tauri app, and the look in the macOS menu bar and the Windows tray was not checked.
