# ClawdMeter architecture

Technical document for whoever maintains the app. To install and use it, see the [README](../README.md); to run and contribute, [DEVELOPMENT.md](DEVELOPMENT.md); for the process policy, secrets, capabilities and security backlog, [SECURITY.md](SECURITY.md).

Tray app for macOS, Windows and Linux (x86_64). On macOS it lives in the menu bar; on Windows, in the notification area; on Linux, in the AppIndicator / StatusNotifierItem tray, where the icon only opens a menu (**Open panel**, **Quit ClawdMeter**). One click on the icon (on Linux, **Open panel**) opens a popover with the enabled pages (Usage, Sessions, Pull Requests, Reviews, Agenda and Skills).

Stack: Tauri 2 (Rust only in the platform layer), TypeScript, Angular 21 (standalone + signals).

## Pages

| Page | Id | Polling | Connections | What it shows |
|---|---|---|---|---|
| Usage | `usage` | 5 min | Claude | bars for the 5 h and 7 d windows with a vertical mark at the % projected at reset, and a chart (1h, 6h, 1d, 7d, 30d or the weekly "Reset" cycle) with both series and the trend |
| Sessions | `sessions` | 5 s | none | open Claude Code sessions and the ones that need attention |
| Pull Requests | `prs` | 5 min | GitHub | my open PRs per repo |
| Reviews | `reviews` | 5 min | GitHub | PRs to review and reviewed ones (open and from the last 30 days) |
| Agenda | `teams` | 10 min | Microsoft | today's Outlook/Teams meetings, with **Join** |
| Skills | `skills` | no polling | Notifications | runs Claude Code skills (`claude -p`) with streaming, cancel and history |

Each one can be turned on and off in Settings. A page only runs if the connections it requires (`requiredConnections`) are ok; otherwise it shows the fix button. A page can also list `optionalConnections(settings)`: they show up in Settings > Connections while the page is on, but never block it. Usage lists Notifications while any usage alert is selected, since the alerts are silent without it.

## Settings

The ⚙ button in the bottom right corner is the only way in. Pages (checkboxes generated from the registry), appearance (language, accent color and popover background from a preset palette or a typed hex; light/dark/system theme) and the Usage alert thresholds apply immediately through CSS custom properties and are saved to `settings.json` in the OS config folder (`appConfigDir`):

| OS | Path |
|---|---|
| macOS | `~/Library/Application Support/com.mottu.clawdmeter/settings.json` |
| Windows | `%APPDATA%\com.mottu.clawdmeter\settings.json` |
| Linux | `$XDG_CONFIG_HOME/com.mottu.clawdmeter/settings.json` (`~/.config/…` by default) |

The file has a `schemaVersion`; old versions are migrated and rewritten on read, and future versions are never rewritten at boot (no downgrade). Editing the file by hand while the app is open reloads the settings.

A `settings.json` with invalid JSON is never overwritten: the app uses the last valid state in memory (or the defaults, if the boot already found it broken) and only writes the defaults when the file does not exist. While the file is broken, changes made in the UI apply to the session but are not persisted; once the file is fixed, the app reloads the content from disk. A read or write failure shows up as a warning at the top of the popover.

**Language:** `settings.language` (`en` default, `pt-BR`, `es-MX`), in the Settings > Appearance selector; it applies immediately. A file without the field (older versions) now opens in `en` (`schemaVersion` 3 is unchanged, and there is no forced migration: whoever already saved a language keeps it). The typed dictionaries live in `src/ui/i18n/{en,pt-BR,es-MX}.ts`: `en.ts` defines the keys (`MessageKey`), and the other two are `Record<MessageKey, string>` (the compiler catches a missing key) and `i18n.spec.ts` checks key and placeholder parity. The `Localizer` (`ui/i18n/localizer.ts`) translates with `t(key, args)` and formats dates, times, durations, numbers and cost with `Intl` in the chosen language; the `I18n` service exposes the `Localizer` as a signal, so switching updates the screen without a reload. The `domain` has no UI text: connection problems (`ConnectionProblem`), fixes (`FixAction`/`ActionLabel`), status notes (`StatusNote`) and app errors (`CodedError`/`ErrorCode`) are codes that the UI maps to keys (`problem.*`, `action.*`, `note.*`, `error.*`). Notifications and the tray tooltip are built by the `Translator` port (`application/ports/translator.ts`, implemented by `LiveTranslator` and bound to the current language in `CurrentLanguage`); switching language re-reads Usage to update the tooltip. The demo opens in `en`, and `?lang=pt-BR` (or `es-MX`) saves the language before boot. The user-facing messages coming from infrastructure (network failure, GitHub Device Flow, GraphQL rate limit, untitled meeting in the agenda) are dictionary keys in all three languages. Technical error messages (Rust `CommandError`, exceptions) are in English and are not translated. Run errors already stored in `runs.json` keep whatever language they were saved in.

**Usage alert thresholds:** `settings.usageThresholds` (`warning` 70 and `critical` 90 by default), editable in Settings; `0 < warning < critical ≤ 100` must hold (an invalid value is ignored in the UI, in the patch and in the migration).

**Usage alerts (quartiles):** `settings.usageAlerts` (`{ fiveHour: Quartile[]; sevenDay: Quartile[] }`, `Quartile` = 25, 50, 75 or 100; default `[50]` in both; schema 9, added by migration 8 → 9). Settings > Usage alerts has one row of checkboxes per window and applies immediately; an empty list means no alert for that window, and lists are always sorted, without duplicates and with valid quartiles only (an invalid value is ignored in the patch and replaced by the default in the migration). `domain/usage/usage-alerts.ts` (`evaluateUsageAlert`) is pure: given the in-memory state of a window (`reached` quartile and last `resetsAt`), the reading (`utilization` in %, 0–100 as the API returns it) and the selected quartiles, it returns the highest selected quartile crossed and not yet alerted, plus the new state. Each quartile alerts once per cycle, and when several are crossed at once only the highest one alerts. The cycle restarts from zero (and may alert normally) when `resetsAt` changes by more than 1 min (both non-null). A drop in utilization restarts it only when it falls more than `DROP_MARGIN` (5 points) below the last quartile reached; that restart is silent and sets `reached` to the highest quartile at or below the new reading, so smaller oscillations around a quartile never alert twice. Runs of `NotifyUsageQuartiles` are serialized in call order, each notification is sent on its own (one failing does not block the other window), and the title percentage is floored (never below the quartile alerted). The first reading after the app opens only sets the state (no retroactive alert). The state is kept per Claude account (a map by `accountId`), only the active account is evaluated (a reading of an account that is no longer active is ignored) and the first reading after switching accounts is silent too. `NotifyUsageQuartiles` (`application/use-cases/usage`) is an optional dependency of `LoadUsage`, called after the snapshot without being awaited: it reads the preferences, and sends one notification per window through the `Notifier` only if the `notifications` connection is `connected`; when a quartile is due and the permission was never asked (`disconnected`), it asks the OS once through `connections.connect` and sends only if that ends `connected`; any failure is swallowed and never breaks the usage load. The title carries the window and the percentage (`notice.usage.title`) and the body says when it resets (`notice.usage.body.resets`) or a simple text when `resetsAt` is missing.

**Claude accounts:** `settings.claude` (`{ useDefaultClientId: boolean; clientId: string; accounts: { id: string; name: string }[]; activeAccountId: string | null }`; schema 10, added by migration 9 → 10 with `useDefaultClientId: true`, `clientId: ''` and zero accounts). The OAuth client id sent to Rust always comes from `effectiveClaudeClientId(claude)` (`domain/settings/claude-accounts.ts`): `DEFAULT_CLAUDE_OAUTH_CLIENT_ID` (`9d1c250a-e61b-44d9-88ed-5944d1962f5e`, the public client id ClaudeUsageBar uses; this constant is the only place that holds the value and the UI never shows it) while `useDefaultClientId` is `true`, otherwise the custom `clientId`; no consumer reads `claude.clientId` directly. `clientId` holds only the custom id (a UUID in lowercase, or `''` when there was never one) and is kept when the default is turned back on, so it fills the field again. `useDefaultClientId: false` only exists together with a valid custom UUID. The normalization (migration and `normalize`, through `readClaudeClientIdMode`) also reads the schema 10 files written by the earlier beta, which had no `useDefaultClientId` and stored the default id in `clientId`: without the flag, a missing, invalid or default `clientId` (case-insensitive) becomes `true` with `''`, and any other valid UUID was a custom id, so it becomes `false` with that id; a boolean flag is respected, except `false` without a valid UUID, which falls back to `true`. In the patch, `useDefaultClientId: true` always applies (the custom id stays stored), `false` applies only when the resulting `clientId` is a valid UUID, and an invalid `clientId` is ignored and never turns the default off. Up to 5 accounts (`MAX_CLAUDE_ACCOUNTS`); `id` is a UUID v4 from `crypto.randomUUID()` (only `[A-Za-z0-9-]`), `name` is required, trimmed, at most 40 characters and unique ignoring case. `activeAccountId` always points to an existing account, or is `null` without accounts: a missing or unknown active id moves to the first account, and removing the active account activates the first remaining one. The patch replaces the account list only when every entry is valid; the migration drops the invalid entries. Every change to this section goes through the account use cases (`application/use-cases/claude-accounts`) and the shared `UpdateSettings`, which serializes all `settings.json` writes (Settings screen and accounts) and notifies the `SettingsSession`, so the screen picks up the new accounts right away and a pending write of the screen never brings back an older account list.

**Usage tab blocks:** `settings.usageBlocks` (`{ modelLimits: boolean; extraUsage: boolean; resets: boolean }`, all `true` by default; schema 11, added by migration 10 → 11, which fills the three flags). Settings > Usage tab has one checkbox per block and applies immediately; a value that is not a boolean is ignored in the patch and replaced by `true` in the migration, and unknown keys are dropped. The resets switch also decides whether the resets are read at all (see Claude usage).

The native color picker (`<input type="color">`) is forbidden in the `ui`: it opens in a separate window and the popover closes because it loses focus. The architecture lint blocks its use.

## Theme and colors (Mottu DS)

The source of truth for colors is Mottu's external DS (`@mottu-ops/ds-core-external`, private GitHub Packages, **not** a dependency of the app). `src/ui/theme/mottu-tokens.scss` is a snapshot, with the same `--me-*` names, of only what the app uses (primary, warning, alert, info and neutral scales, `*-base/-dark/-alt/-light` aliases, `background-change`/`component-change`/`text-change`, radius 2/4/8/16/1000 and shadow 1/2/3). `mottu-tokens.ts` mirrors in hex what ECharts needs (canvas does not resolve `var()`), and `tools/theme-tokens.spec.ts` proves the two match. To update, copy the values from the package's `dist/mottu-ds.css`.

`theme.scss` defines the app vars (`--cm-*`) on top of the tokens via `var(--me-*)`. Components use only `--cm-*`; hex outside `src/ui/theme` and `domain` is blocked by a test.

| Theme | Popover | Cards | Text | Secondary text |
|---|---|---|---|---|
| Dark | `#1a1a1a` (between `neutral-10` and `neutral-20`) | `#202022` | `neutral-95` | `neutral-70` |
| Light | `neutral-99` | `neutral-100` | `neutral-10` | `neutral-40` |

Soft look: the Tauri window is `transparent: true` (on macOS it requires `app.macOSPrivateApi: true` and the `macos-private-api` feature of the `tauri` crate) and `.popover` draws 12 px corners (`--cm-radius-window`) with a 1 px translucent border (`--cm-edge`, 8% of the text) and the native window shadow (`shadow: true`; a CSS shadow would be clipped at the window edge). `html` and `body` are transparent and `color-scheme` is set on `cm-root`, never on `:root`, otherwise the browser paints the canvas and the corners go square again. Cards, controls and separators use translucent borders (`--cm-border` 6%, `--cm-control-border` 14% only on buttons and fields), a 12 px radius on cards (`--cm-radius-md`) and 8 px on controls; tabs and period selectors are pills with the active segment in green. A custom background recomputes these variables from the text color (`BACKGROUND_OVERRIDES` in `theme-style.ts`). The dark hex values (`soft-surfaces.ts`) sit between the DS `neutral-10` and `neutral-20`, and `tools/theme-tokens.spec.ts` checks that.

- **Accent = Mottu green** (`--cm-accent`, default `#00b131` = `primary-base`): active tab, primary buttons (the `me-button` recipe: radius 2px, `:active` in `primary-dark`), period selector, focus, checkbox, "now" and "next" in the agenda. Text and thin lines use `--cm-accent-text`: `primary-alt` (`#1bd60b`) in dark, `primary-50` in light. The text on top of the accent is chosen by WCAG contrast (dark `#121212` or white, whichever passes AA); on the base green it comes out dark. A custom accent color applies to all of this, charts included.
- **Semantic:** error = `alert`, warning = `warning`, info = `info`, success = `primary` (`--cm-danger`, `--cm-warning`, `--cm-info`, `--cm-ok`; the `*-text` variants use the DS step with contrast in each theme).
- **Usage:** by default 5h is `primary-alt` in dark and `primary-base` in light (or the chosen accent color) and 7d is gray (`--cm-series-five` and `--cm-series-seven`), in the bar and in the chart. In Settings, in the collapsible "Usage lines" section (closed by default; the header shows the current 5h and 7d colors), "5h" and "7d" (same preset selector + validated hex, with "Use default color") save `seriesColors: { fiveHour, sevenDay }` in `settings.json` (schema 7; `null` = theme default, so the default keeps following light/dark and the accent color). The chosen color applies to everything that draws the series: bar fill, projected mark, "Projected" dot, chart legend, actual line, area, dashed trend and tooltip dot. No text is painted with the series color (percentages, labels and tooltip use the theme text color), so a color that is too dark or too light for the background never makes text unreadable; the line keeps exactly the chosen color. The band colors (gray, yellow `#FFC700`, red `alert-base`) apply only to the 7d projection (dashed trend, vertical mark on the bar and the "Projected N%" legend), by the band of the projected % and the Settings thresholds; the 5h projection is green and turns red from 100%.
- **PR SLA (Pull Requests and Reviews):** age badge and a mark on the row's left border, by the age since opening of open PRs (`domain/pull-requests/sla.ts`): under 3 days neutral, 3 to 6d23h yellow `#FFC700` (Yellow 1 of the official palette; the external DS has no yellow) with dark text, 7 days or more `alert-base`. In Reviews the reference is also the opening: the PR model does not carry the review request date. Red on these pages only appears for failing CI and conflicts; "Changes requested" uses `info`.
- **Font:** `"Helvetica Neue", Helvetica, Arial, sans-serif` across the app (`--cm-font-family`) and in the ECharts `textStyle`. There is no other font.
- **Migration:** `schemaVersion` 2 swaps the old accent `#6366f1` (indigo, the old default) for `#00b131`. Whoever chose another color keeps theirs; whoever had chosen the indigo on purpose is also migrated, because the value equals the old default.

## Connections

Settings has a **Connections** section with the connections required by the enabled pages (`PageModule.requiredConnections`). Each one has a status and the fix button for the current state; every disconnectable connection has **Disconnect**.

| Situation (`ConnectionProblem`) | Button |
|---|---|
| `claude-no-account` (no Claude account, or none active) | Add account (opens Settings > Claude accounts) |
| `claude-signin-required` (the active account has no tokens, or Rust could not refresh them) | Sign in again (opens Settings > Claude accounts and starts the sign-in of that same account) |
| `github-unauthorized` | Sign in to GitHub again |
| `github-missing-scope` | Redo permissions |
| `github-org-access` (pending SSO) | Authorize for the org (opens the SSO URL sent by GitHub in the `x-github-sso` header, only if it is https on github.com) |
| `github-not-member` | Open the org page |
| `microsoft-expired` | Sign in to Microsoft again |
| `microsoft-not-connected` | Connect |
| `notifications-blocked` (denied) | Open system settings |
| `notifications-unverifiable` (OS has no way to tell) | Open system settings (the row shows "Cannot verify", never "Connected") |
| `unexpected` (network etc.) | Try again |

- **Claude:** each account signs in with the app's own OAuth flow (PKCE S256 in the browser, loopback listener on `127.0.0.1` with `http://localhost:<port>/callback`, or a pasted `code#state` from the code page); details and limits in [SECURITY.md](SECURITY.md#claude-accounts-own-oauth-sign-in). The access and refresh tokens are kept in the OS keyring (service `com.mottu.clawdmeter`, key `claude.account.<accountId>`, outside `ALLOWED_SECRET_KEYS`) and never leave Rust: the webview only receives `{ loginId, authorizeUrl, state, redirectUri, manualAuthorizeUrl }` from `claude_oauth_begin`, `{ expiresAt, email }` from `claude_oauth_complete`, `{ signedIn, expiresAt, needsLogin }` from `claude_account_status` and the usage JSON from `claude_usage_fetch`. Rust refreshes the tokens itself (5 minutes before expiry, or once after a 401), one refresh at a time per account; `claude_oauth_cancel` drops a pending sign-in and `claude_account_remove` deletes the account's tokens locally (no remote revocation). Rust reads each keyring item (these tokens, `github.token`, `microsoft.refresh-token`) once per run (a denied prompt is asked again only after 30 minutes; a Claude account is read again right before its refresh token is spent, in case another app instance renewed it) and serves later reads from memory, so polling does not bring the Keychain prompt back; saves and deletes can still prompt on macOS ([keyring cache](SECURITY.md#keyring-cache)).
- **GitHub:** `gh auth token` (the token is not copied; the port returns `{ token }` or `{ missing: 'not-installed' | 'not-logged-in' }` and the row shows the right button for each reason) → sign in with the browser (Device Flow) → pasted PAT (the last two are kept in the OS vault). Validation checks scopes (`repo`, `read:org`) and access to the `Mottu-ops` org.
- **Microsoft:** PKCE with a listener on `127.0.0.1` (ephemeral port); the refresh token is kept in the OS vault. Delegated scopes `Calendars.Read` + `offline_access`; no client secret.
- **Notifications:** the Tauri plugin always returns `granted` on desktop, so the state comes from the `notification_permission_state` command (macOS: `UNUserNotificationCenter`, only in the packaged app; Windows: `ToastNotifier.Setting`; Linux: `granted` when a notification server answers `GetServerInformation` on the session bus through `notify-rust`, the same library the plugin sends with, since freedesktop notifications have no per-app permission, otherwise `unknown`; anywhere else `unknown`). The plugin's request is a no-op on desktop too, so the app asks through the `notification_permission_request` command (macOS: `requestAuthorizationWithOptions` with alert and sound, waiting up to 120 s for the answer, then reading the state again; elsewhere it only reads the state). `prompt` (never asked) is `disconnected` with the `notifications-not-authorized` note and a **Connect** button that runs that request; macOS only lists the app under System Settings > Notifications after this first request. `denied` leads to **Open system settings**. When a skill run ends, the app sends a local notification only if this connection is `connected`.
- **GitHub Device Flow:** has a Cancel button (`AbortSignal`, also passed to the polling `fetch`); opening "Paste token" also cancels. On start, the UI shows the code with a Copy button and the instruction to paste it on the page that was opened. A result that arrives after the cancellation is discarded before writing to the vault.
- **Claude connection state:** `CheckClaudeConnection` reads `settings.claude` and asks Rust for the active account's status (`claude_account_status`): without an active account the row says to add one (`claude-no-account`); `signedIn: false` or `needsLogin: true` gives `claude-signin-required` with the account name in the message (`error.claude-signin-required`); otherwise the row shows "Connected · <account name>". The connection only covers Claude usage: Skills runs Claude Code with its own login and no longer requires it, and the PRs pages and GitHub are unchanged. The two fixes need the user, so the UI handles them (`ConnectionsFacade`): both open Settings at the **Claude accounts** section (`ShellNavigation.openSettings('claude-accounts')`, which expands and scrolls to it), and "Sign in again" also starts the sign-in of the active account there; `FixClaudeConnection` itself only checks again.
- Non-secret preferences (GitHub method, Microsoft account, Claude enabled) are kept in `connections.json` next to `settings.json`.
- A `keychain` error from Rust (any keyring failure, a denied prompt included) is a generic storage error: `unexpected` with the `keychain-unavailable` message and "Try again".
- A `keyring_unavailable` error (Linux only: no Secret Service, or no session bus, answered) is `unexpected` with the `keyring-unavailable` message, which names GNOME Keyring and KWallet and says nothing was saved. There is no fallback storage.

The GitHub OAuth App and Entra ID `client_id`s are placeholders in `src/infrastructure/config/auth-config.ts` (`REPLACE_WITH_…`); while they are placeholders, Device Flow and Microsoft login fail with an `unexpected` state explaining what is missing. A gateway problem (e.g. `claude_signin_required` from the Claude usage) marks the connection with `connections.report.execute(id, problem, message, code, args)`.

## Claude accounts

Settings > **Claude accounts** (`ui/settings/claude-accounts`, state in `ClaudeAccountsFacade`) lists the accounts (name, "Active" badge, a status from `claude_account_status` that describes the state: "Connected", "Signed out" without tokens or "Session expired" when Rust needs a new sign-in; a healthy account never shows the expiry because Rust renews the token by itself; and **Sign in again**, **Rename** and **Remove** with an inline confirmation), the **Add account** form (required name, checked with `accountNameProblem` before the browser opens and shown next to the field; the typed name survives a failed or cancelled sign-in; disabled with the explanation at 5 accounts) and the **Use default client ID** choice (a `role="radiogroup"` of **Yes**/**No**, **Yes** by default, with roving `tabindex` and the arrow keys moving the choice; the hint says a change only applies to the next sign-ins and accounts already signed in keep the client ID of their sign-in). With **Yes** there is no field and the default id is not shown anywhere. **No** shows the field for a custom UUID (neutral `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` placeholder and format message, **Save**); choosing **No** changes nothing in the settings until a valid UUID is saved (the choice and the draft stay local, and the hint says the default is still in use), the field starts with the custom id already stored, and going back to **Yes** discards the draft and, when **No** was saved, persists **Yes** right away. The choice and the field are disabled while a sign-in is open. One `role="status"` line, always in the DOM, announces the start, the wait and the outcome ("Work added", "Work connected again"); the sign-in block moves the focus to **Cancel** and **Paste code** to the code field. The section opens by itself only when it is first shown without accounts. The view rules are pure functions in `claude-accounts-view.ts`.

- **Adding** (`AddClaudeAccount`): validates the name and the limit, generates the id, calls `claude_oauth_begin({ clientId })` with the effective client id, opens `authorizeUrl` with the external URL opener and waits on `claude_oauth_complete({ loginId, accountId, timeoutMs: 300000 })` (5 min) while the section shows "Waiting for the browser" with **Cancel** and **Paste code**. Only after Rust returns does the account get written to the settings (active when it is the first); a cancel, a timeout or an error writes nothing and calls `claude_oauth_cancel` (the pending sign-ins share a limit of 2 in Rust, so every abandoned sign-in is cancelled: Cancel, also while the browser is still opening, leaving Settings, collapsing the section, timeout or error). A 429 from the token endpoint becomes `claude-login-rate-limited`. Known limit: Rust reports the end of the browser wait and a timeout of the token exchange with the same `timeout` kind, so both show as `claude-login-timeout`. If the cancel arrives after Rust already stored the tokens, they are deleted with `claude_account_remove`; if the settings cannot be written, too.
- **Paste code** (`OpenClaudeLoginCodePage` + `CompleteClaudeLoginWithCode`): opens `manualAuthorizeUrl` (same state and challenge, redirect to the code page) and sends the pasted `code#state` with `claude_oauth_complete({ loginId, accountId, code })`. A code whose state matches takes over the sign-in in Rust and the browser wait ends as `cancelled`; whichever path succeeds records the account once (`PendingClaudeLogin`), and a code refused by the token exchange ends that sign-in without writing anything. A code of another sign-in (`claude-login-code-invalid`) keeps the sign-in alive, so the user can paste again and a later timeout or failure of the browser wait still reaches the user; only the `cancelled` end caused by an accepted paste is silent.
- **Sign in again** (`ReauthenticateClaudeAccount`): the same flow with the same `accountId`; the settings do not change. If the account left the settings while the browser was open, the tokens Rust just stored are deleted and the sign-in ends with nothing to report.
- **Rename** (`RenameClaudeAccount`), **Select** (`SelectClaudeAccount`, persists `activeAccountId`) and **client id** (`SetClaudeClientIdMode`: `{ useDefault: true }` persists right away and keeps the stored custom id; `{ useDefault: false, clientId }` validates the UUID, stores it in lowercase and refuses an invalid or empty one with `claude-client-id-invalid` without writing) only write the settings. **Remove** (`RemoveClaudeAccount`) first cancels a pending sign-in of that account, then deletes the tokens in Rust (a failure keeps the account), then the account (the active one moves to the first remaining) and then, best effort, its history file. While a sign-in is open the rows disable **Remove** and **Rename**, and `ClaudeAccountsFacade.remove` refuses (`claude-login-busy`) while any sign-in is starting or while the account itself is waiting for the browser.
- **Switch:** in the tab row, only while the Usage page is shown and there are 2 or more accounts, a compact button with the initials of the active account opens a list with the full names (`cm-account-switch`: `aria-haspopup="listbox"`, `role="listbox"`/`option`, arrows, Home/End, Enter/Space, Escape and Tab; it closes on an outside click). It sits at the right of the tabs as a compact button with the initials of the active account (at most two; the full name is in the accessible name, the tooltip and the list, which is at most `min(340px, 100vw - 24px)` wide), about 40 px, so at 380 px the four default tabs (Usage, Sessions, Pull Requests, Reviews) fit whole in the three languages; with Teams and Skills on, the tabs scroll horizontally as before. The button cancels its own `mousedown`, so WKWebView, where a click does not focus a button, does not close and reopen the list. Choosing an account persists it, checks the Claude connection again and reloads Usage right away with `scheduler.refresh('usage', { resetBackoff: true })`: the rate-limit backoff belonged to the previous account, so the new one is not kept waiting. A failure to switch shows in the error bar of the shell for 10 s. No other page shows it.
- **Per-account state:** the history is one file per account (below), `UsageData` carries the `accountId` and the Usage view ignores data of an account that is not the active one (it shows "Loading…" instead of the previous account's numbers until the new read arrives); the tray icon and the quartile alerts follow the active account. `LoadUsage` reads the active account again after the fetch: a reading that arrives after a switch still goes to the history of its own account, but neither it nor a failure of the previous account touches the tray or the Claude connection. A late reading of the previous account also makes the next reading of the active one silent for the quartile alerts.
- **Demo:** `yarn dev:web` seeds two fictitious accounts (Personal and Work) in the demo settings, each with its own deterministic usage, so the switch shows up on Usage; the demo sign-in completes by itself after 2.5 s (or right away with a pasted code). `?demo=claude:claude-signin-required` makes the first account ask for a new sign-in and `?demo=claude:claude-no-account` starts without accounts.

## Claude usage

`usage` page (5 min poll, requires the Claude connection). `LoadUsage` reads the active account and the effective client id (`effectiveClaudeClientId`) from `settings.claude` (no active account fails with `claude-no-account` without calling Rust) and calls the `AnthropicUsageGateway`, which invokes the `claude_usage_fetch` command with `{ accountId, clientId }`: Rust loads that account's tokens from the keyring, refreshes them when needed (see Connections above) and does the `GET https://api.anthropic.com/api/oauth/usage` (header `anthropic-beta: oauth-2025-04-20`), so the token never reaches TypeScript; the response is limited to 256 KiB (`Content-Length` is checked first and the body is read in chunks, cutting off past the limit, even without `Content-Length`). No tokens, an expired token without a refresh token, a refused refresh or a 401 after the renewal give `claude_signin_required`; the tokens are kept but marked, so `claude_account_status` reports `needsLogin` and later fetches fail fast until the account signs in again. The fields read are `five_hour` and `seven_day` (`utilization`, `resets_at`); the parse ignores extra fields and windows without a valid `utilization`.

- **Blocks below the bars:** three optional blocks, in this order, between the 5h/7d bars and the chart, each with a switch in Settings > Usage tab (`settings.usageBlocks`, `{ modelLimits, extraUsage, resets }`, all `true` by default; schema 11, added by migration 10 → 11). A block that is off is not rendered, and a block that is on but has no data from the account is not rendered either, with no error. `parseUsageResponse` reads them from the same `/api/oauth/usage` answer as the bars, additively (`UsageSnapshot.modelLimits` and `extraUsage`; `fiveHour`/`sevenDay` and `UsageWindowKind` are unchanged), so these two blocks cost no extra request. **Model limits:** one bar per row of `limits[]` that has `scope.model.display_name` and is not a `session` row (name as the API sends it, `percent`, `resets_at`), plus `seven_day_opus` and `seven_day_sonnet` (named Opus and Sonnet) when present and not already covered by a `limits[]` row whose name contains that model (case-insensitive); the same name twice in `limits[]` keeps the higher percent. No history, projection, quartile alerts or tray icon for them. **Extra usage:** `extra_usage` (`is_enabled`, `currency`, `monthly_limit`, `used_credits` in minor units, `decimal_places`, `utilization`); the percent is `utilization`, or `used_credits / monthly_limit` when `utilization` is null (it is null on the account that was probed), and the amounts are formatted by `Localizer.money` in the account currency. A block without a 3-letter `currency` is treated as absent. **Resets (read only):** `cedar_ember` from the second read, `claude_usage_resets_fetch`, which Rust sends as `?cedar_ember=1&skip_spend=1` (see [SECURITY.md](SECURITY.md)). `UsageResetsMonitor` (`application/usage-resets`, started from `SettingsFacade` like the scheduler) polls it on its own timer, every 15 minutes: grants change on a scale of days, the endpoint is undocumented and rate limited, and the usage poll already runs every 5 minutes, so a slower read keeps the extra load small; it reads once when the block is switched on or the active account changes and never while the block is off (`LoadUsageResets` also checks the switch). Any failure, a 429 (it waits out the same backoff as the usage page), an ineligible account (`eligible: false`), no grants or a missing block publishes nothing, which hides the block; it never touches the bars or the chart. Unknown or malformed grants (no `id`, or a `type` other than `session`, `weekly`, `full`) are skipped, and `clears` falls back to the type when it is missing or unrecognized. The block shows the total of resets left (grants that have not expired) and, per grant, the type, what it clears, uses left, expiry and whether it is usable now (`usable_now`, not paused, uses left, not expired). **Recommended grant** (`recommendedGrant`, pure): the windows the user is blocked on are those at 100% or more, the ones the API lists in `exhausted` and, if `at_limit` is true with neither, both windows; the recommended grant is the usable one that clears any of them and expires first (a grant without expiry comes last; on a tie, the one that clears fewer windows, so a full reset is not wasted). When the user is not at a limit there is nothing to clear, so no grant is highlighted. There is no action to use a reset anywhere in the app. The demo mode (`DemoUsageResetsGateway`, plus model limits and extra usage in `DemoUsageModel`) feeds the three blocks.

- **History:** one file per account, `usage-history.<accountId>.json` next to `settings.json` (`JsonUsageHistoryStores`, one cached store per account). The single `usage-history.json` of the versions before the accounts is adopted by the first account created: if it exists and the account has no file yet it is renamed to that account's file before the account is written to the settings (and renamed back if that write fails), so nothing is lost. Later accounts start with an empty history already marked as imported, so the ClaudeUsageBar history below only goes to the account that received the legacy history (or to the first account of a fresh install). Removing an account deletes its file (best effort; it needs `fs:allow-remove` on `$APPCONFIG/usage-history.*.json` in the capability). Raw points for 7 days; from day 8 to day 30, aggregated into 15 min buckets by the maximum; nothing goes past 30 days (`domain/usage/retention.ts`). It stays in memory after the first read and is written serially through a temporary file + `rename` (`fs:allow-rename` only in `$APPCONFIG`). An unreadable file becomes `usage-history.<accountId>.json.corrupt` and the history restarts empty, without overwriting the original.
- **ClaudeUsageBar history (one-time migration):** on the first successful load, `ImportExternalUsageHistory` reads `~/.config/claude-usage-bar/history.json` (`{"dataPoints":[{"timestamp","pct5h","pct7d"}]}`, fractions 0–1) through the `ExternalUsageHistorySource` port (adapter `TauriClaudeUsageBarHistorySource`; in the demo, an empty fake), merges it into the history before retention and writes the `claudeUsageBarImportedAt` marker in the account's history file itself. After that the file is never read again: from then on the history belongs to ClaudeMeter itself. Anyone who already has any point with the `imported` mark in the account's history is treated as already migrated, without reading the file. A missing or unreadable file counts as an empty source and also completes the migration; only an unexpected failure of the source retries on the next load. On merge, a fraction becomes %, points within 1 min of an existing point (or of each other) are discarded and our point wins, nothing older than 30 days or in the future gets in, and normal retention (raw 7 d, 15 min buckets up to 30 d) applies to the imported ones. The imported point has no `resets_at`: it carries the `imported` mark (4th element of the point) and cycle detection ignores the `resets_at` comparison on pairs with an imported point. The capability gives the plugin-fs only `read-text-file` on `$HOME/.config/claude-usage-bar/history.json` (needed for whoever installs now and has the file; `tools/capabilities.spec.ts` checks the scope). There is no toggle in Settings.
- **Transient error:** if a refresh fails (network, 5xx), the page keeps the last data and shows the error banner on top, with "Showing the last loaded data."
- **Rate limit (429/5xx):** Anthropic returns 429 on `/api/oauth/usage`. Rust passes the `rate_limited` `kind` with an optional `retryAfterSecs` (a generic HTTP 429/5xx error also counts) and the gateway converts it into `RateLimitedError`. The `PollingScheduler` postpones the page's next poll to `max(Retry-After, 5 → 10 → 20 → 30 min)` (`domain/rate-limit.ts`), including the manual refresh, and goes back to the normal pace after a success; a change of the active account clears it. The banner says "Anthropic rate limit — trying again in 12 min", with no API path, keeping the last data.
- **Refresh:** the ↻ button in the footer (left of the gear) reloads the current page through `scheduler.refresh`; it spins while loading, has a 30 s cooldown and, during a rate limit backoff, shows the remaining time in the tooltip without calling Anthropic (`ui/shell/refresh-state.ts`).
- **Layout:** at the top, two bars (`5h` and `7d`) with the percentage on the right and "resets in 2h06" below; the value predicted at reset is a thin vertical line (2 px, a bit taller than the bar) at the projected % point, in the projection color (at the end of the bar and red if it goes past 100%, and the legend carries the real number, e.g. "Projected 132%"; no mark when there is no projection). Below, the `1h · 6h · 1d · 7d · 30d · Reset` selector (segmented control, default 6h; "Reset" shows the weekly cycle, from the 7d `resets_at` − 7 days to the next reset, with subtle marks at "now" and at the 5h resets in the interval, and is disabled without a known `resets_at`) and a single ECharts chart (via `ngx-echarts`, loaded on demand) with both series on the same axis (Y axis on the right, from 0 to 100% in steps of 25; when the drawn projection goes past 100%, the axis rises to the next multiple of 25 above the projected maximum, capped at 300% and in steps of 50 above 200%), smooth lines with a very light area, dashed grid, dashed vertical marks at "now" and at the resets that fit the axis, a solid subtle reference line at 100% (red with low alpha, only with the expanded axis, and a highlighted "100%" label on the axis) and a `● 5h ● 7d` legend. There are no forecast sentences or long titles.
- **Chart (smooth curve, like ClaudeUsageBar):** the visible period (from the start of the axis to now) is split into 120 buckets (`CHART_BUCKETS`); each bucket with a reading becomes a point with the average of the % and the average of the instant, and an empty bucket is discarded (`downsample` in `usage-chart-model.ts`). The points are joined by a smooth curve (`smooth: 0.5` in ECharts), with no steps and no special handling of gaps or resets. The tooltip for the past interpolates on the curve with Catmull-Rom (`curveValueAt`); after the last point it shows the last value. The dashed projection does not use the buckets: it starts from the last real reading.
- **Projection (a single rule, chosen in Settings > Projection):** `projectionMethod` in `settings.json` (added in schema 6; default `7d` since schema 8). Selector order: Last 24h, Last 7 days, Last 14 days, Since reset. `ProjectUsage` (`application/use-cases/usage`) computes ONCE per render `{ rate, valueAtReset, resetsAt, trend }` for 5h and 7d, and bars, dashed line (all periods and the Cycle), future tooltip and the "Projected N%" legend only read that result (`domain/usage/forecast.ts`); the chart-model recomputes nothing. 7d methods: `24h` (rate = sum of the positive 7d increments in the last 24 h ÷ hours covered, drops are resets and ignored; without 2 h of data it falls back to `since-reset`), `7d` (default: the sum of the positive 7d increments in the last 7 × 24 h ÷ 7 calendar days, so a gap without readings counts as zero consumption; with less than 1 day of data in the window it falls back to `since-reset`), `14d` (the same increments over the last 14 days ÷ the days actually covered, minimum of 1 day of data, otherwise `since-reset`) and `since-reset` (rate = current % ÷ time since the last reset, `resets_at` − window duration; with less than 30 min elapsed there is no projection). In all of them, projected = current + rate × time until reset. 5h always uses `since-reset`, whatever the choice (the option in Settings carries the help line). The line has the series color, dashed, from the current point to `resets_at` (cut at 100% outside the Cycle; the Cycle expands the axis, capped at 300%), with a "date + Projected N%" tooltip in the Cycle. The linear regression was removed. Migration 7 → 8 turns every saved `14d` into `7d`: the old default was written by migration 5 → 6, so a file cannot tell an explicit `14d` from the default, and whoever wants 14 days picks it again (a `14d` saved after schema 8 is kept). The tray shows only current usage (percentages and reset times), not projection.

## Usage icon in the tray

On every `LoadUsage` read of the active Claude account (and on every failure) the `UsageIndicator` port updates the tray icon and tooltip through the `tray_set_usage` command; in the demo the adapter is a no-op.

- **macOS:** wide icon (template, only alpha counts) with the pixel mascot (12×8 grid in `usage_icon.rs`, eyes as holes) on the left and two `5h`/`7d` rows with a rounded bar: filled part opaque, empty at 35%. The mascot fills from bottom to top according to `7d` (0% all at 35%, 100% all opaque) and, when `5h` or `7d` reaches 100% (limit hit), the eyes turn into an X. `tray-icon` fixes the icon height at 18 pt, so the render is 128×36 px (@2x), pixel by pixel at that height.
- **Windows and Linux:** the tray icon is square, so the 32×32 variant (16×16 at @1x) goes with only the mascot (fills with `7d`, eyes as an X when a limit is hit; filled blue, empty gray, readable on light and dark bars). Bars and numbers stay in the tooltip: `5h: 24% · resets 14:09 | 7d: 51% · resets Mon 05:39` (`domain/usage/usage-tooltip.ts`).

Percentages outside 0–100 are clamped in Rust.
- **Before the first read** (and with the Usage page off) the app's default icon applies (`tray-template.png` on macOS, the window icon on Windows); the mascot render only shows up after a read attempt.

## Popover over full-screen apps (macOS)

With another app in full screen (its own Space), a regular window does not show up. In `platform.rs`, `prepare_popover` runs when the window is created and before every `show`: it calls `set_visible_on_all_workspaces(true)` and completes through the `NSWindow` with `collectionBehavior` = `CanJoinAllSpaces | FullScreenAuxiliary | Stationary | IgnoresCycle` (without `FullScreenPrimary`/`Transient`/`MoveToActiveSpace`, which conflict) and level `NSPopUpMenuWindowLevel`. The activation policy stays `Accessory`. On Windows there is no change: the popover is a borderless window with `alwaysOnTop`, and this was not validated on a Windows machine. Only the behavior and level computation has an automated test; the effect over a real full-screen app has to be checked by hand.

To behave as a non-activating panel, `popover::apply` swaps the window's class to `ClawdMeterPopoverPanel` (an `NSPanel` subclass) with `object_setClass`. The swap only happens when the class is exactly `TaoWindow` (and the instance sizes match); a KVO subclass (`NSKVONotifying_TaoWindow`) or any other class is left alone and logged as `panel-class failed class=…`. Known costs of the swap: `TaoWindow`'s overrides are bypassed (`set_focusable()` and dragging the window background stop working, neither is used by the popover), and tao's per-window state is leaked if the window is destroyed. Today the window lives as long as the app, so the leak is bounded to one window; `tauri-nspanel` is the alternative if that changes. A dismiss deferred to the main queue carries the epoch of the show that installed its monitors and is dropped (`dismiss-stale`) if a newer show happened in between. The reopen guard and the dismiss grace use a monotonic clock (an `Instant` taken once per process), so a wall-clock step does not block tray clicks.

`popover.log` lines are written by one background thread. Every build records, on each show, the window frame, level, collection behavior, whether it is on the active Space and whether macOS sees it as visible (`occlusion_visible`), plus the `show+100ms` probe; the activated app (pid and bundle id) is recorded only in debug builds. At startup the app turns off WebKit's window occlusion detection for the popover webview (`webview-occlusion-detection disabled=…`): WebKit stopped painting while it believed the window was covered, so the panel opened blank over a large window.

A second launch of the app does not start a second process: `tauri-plugin-single-instance`, the first plugin in the builder, hands it off to the running instance, which calls `tray::on_second_instance` on the main thread. It logs `second-instance visible=… action=…` and, when the popover is hidden, opens it through the same show path as a tray click, without an icon rect (`None`, as the Ctrl+Alt+D shortcut); unlike a click it never hides an open popover and ignores the reopen guard (`platform::second_instance_action`). See [Two app instances](SECURITY.md#two-app-instances).

On Windows the popover is placed by `tauri-plugin-positioner` (`TrayCenter`, falling back to `BottomRight`) and then clamped to the monitor work area (`rcWork` from `MonitorFromWindow` + `GetMonitorInfoW`), so a taskbar on any edge does not cover it. A failed Ctrl+Alt+D registration (taken by another app, or AltGr on some layouts) is logged as `shortcut-register failed`.

On Linux, tray-icon (libayatana-appindicator) never delivers click events, only menu activations, so `tray::create` adds **Open panel** above **Quit ClawdMeter** (`platform::TRAY_MENU_OPENS_POPOVER`; the native menu strings are English on every system). **Open panel** goes through the same show path without an icon rect and never hides an open popover. `position_popover` takes the monitor under the cursor (falling back to the window's current monitor, then the primary one), reads its work area from Tauri (`Monitor::work_area`, which excludes the top bar and docks) and puts the popover at its top-right corner with an 8 px margin scaled by the monitor factor, clamped with the same `clamp_to_work_area` as Windows (`platform::top_right_of_work_area`, a pure function with tests). On Wayland the compositor may ignore the position. The popover hides on focus loss as on Windows. Ctrl+Alt+D is registered the same way; it works on X11 and usually fails on Wayland, which is logged as on Windows.

## Sessions

`sessions` page (5 s poll, no connection). `TauriSessionDirectory` reads `<home>/.claude/sessions/*.json` (Tauri's `homeDir()`: `~` on macOS, `%USERPROFILE%` on Windows) and `LoadSessions` keeps only the live pids (`process_is_alive`, the F2 Rust command). Each session shows name (or folder), short folder, status (`busy`/`idle`/`shell`) and how long it has been in it (`statusUpdatedAt`, otherwise `updatedAt`). A session that is `idle` for more than 5 min ("Waiting for input for X") or `busy` for more than 30 min ("Busy for X") is highlighted; the thresholds are in `DEFAULT_ATTENTION_CONFIG` (`domain/sessions/attention.ts`) and are injected into `LoadSessions` by the composition root.

**Model, context, tokens and subagents.** `LoadSessions` also takes an optional `SessionUsageReader` (port in `application/ports/session-source.ts`, `TauriSessionUsageReader` in `infrastructure/platform`) and, for each live session with `sessionId` and `cwd`, returns its `SessionUsage` in `SessionsData.usage` (keyed by pid). A session whose read fails or has no transcript is simply missing from the map: its row shows as before and the others are not affected. The reader calls the Rust command `session_usage` (`commands/session_usage.rs`), which opens `<home>/.claude/projects/<cwd with every non-alphanumeric character turned into ->/<sessionId>.jsonl` and keeps an offset per file, so each 5 s poll only parses what was appended. From each `assistant` line it takes `message.model` (skipping `<synthetic>`) and `message.usage`; one API response is written as several consecutive lines with the same `message.id` and the same usage, so it is counted once. The occupied context is `input + cache_read + cache_creation` of the last reply; an `api-request` line whose `params.betas` has a `context-1m-*` beta marks the session as 1M. Subagents come from `<sessionId>/subagents/*.meta.json` without `finished: true` or `stoppedByUser: true` whose `agent-*.jsonl` (or, without one, the `meta.json`) changed in the last 30 minutes, so a subagent killed without being marked does not stay listed; the real model and start come from their own jsonl (the `meta.json` model alias is the fallback). A `<synthetic>` reply (API error or interrupt, every counter at zero) is skipped, so it does not reset the context. The tally map keeps at most 256 files and evicts the least recently read one.

The window per model lives in `domain/sessions/session-usage.ts` (`contextWindow`): Fable/Mythos 5, Opus 5 and 4.6–4.8, Sonnet 5 and 4.6, Haiku 5 have 1M; other Claude 4 and Claude 3 models 200K; the 1M beta wins; a model outside the table shows only `N k`, without a percentage. The row shows the short model (without `claude-`) and `Context N k / window · %` (70% warning, 90% critical). A chevron opens a per-session dropdown with input, cache read, cache write and output tokens summed over the session (no dollar values) and the running subagents with type, model and time alive; **Expand all** / **Collapse all** at the top opens or closes every dropdown (UI state only, not persisted). A `role="radiogroup"` filter at the top (**All** / **Active** / **Inactive**, with counts) uses `sessionActivity` (`domain/sessions/activity.ts`: `busy`, or `idle` for less than `waitingInputAfterMs` of the attention config, is active; longer `idle`, `shell` and unknown are inactive); the summary and **Expand all** apply to the visible rows, and the filter and the open dropdowns live in `SessionsViewState` (root, in memory, not a setting), so they survive switching tabs.

Known limits of the transcript reading:
- A transcript replaced by another file of equal or larger size at the same path (new inode) is not detected; the offset carries over and only a shrink starts the tally over.
- The folder name rule (every non-alphanumeric character becomes `-`) was checked only with plain paths; Claude Code may shorten or hash very long paths (over 200 characters) or treat emoji and other multi-byte characters differently, and then the transcript is simply not found.
- A live subagent that writes nothing to its jsonl for more than 30 minutes (waiting on another subagent or on a long task) drops out of the list until it writes again.
- The 1M flag follows the last `api-request` line only: a session that drops the `context-1m-*` beta mid-way is treated as 200K from then on, and one whose requests are not logged keeps the table value.

The capability gives the plugin-fs only `exists` and `read-dir` on `$HOME/.claude/sessions` and `read-text-file` on `$HOME/.claude/sessions/*.json`; the plugin-http allowlist no longer includes `https://api.anthropic.com` (the usage call is made by Rust; the rest of the HTTP goes through the plugin, so the CSP `connect-src` does not list external hosts).

In demo mode both pages use fake data (30 days of history generated by a deterministic model, five sessions in different states and one dead, three of them with model, context, tokens and subagents). `?demo=claude:claude-signin-required` (and the other connection scenarios) shows the usage page error state with the fix button.

Today's Outlook/Teams meetings, tied to the Microsoft connection, with a 5 min poll.

## Pull Requests and Reviews

Two pages (`prs` and `reviews`, polling every 5 min), each with a single `POST https://api.github.com/graphql` request (several aliased searches, `first: 50` each) using the GitHub connection token (`GitHubTokenResolver`). Access goes through `tauri-plugin-http`; the capability already allows `https://api.github.com/*` and `tools/capabilities.spec.ts` guarantees `/graphql` is covered (the CSP `connect-src` does not come into play, the plugin does not use the WebView).

| Page | Searches |
|---|---|
| Pull Requests | `author:@me is:open is:pr` |
| Reviews: to review | `review-requested:@me is:open is:pr` |
| Reviews: reviewed | `reviewed-by:@me -author:@me` open + closed/merged in the last 30 days |

- Grouped by repo; `k8s` and `k8s-prod` form the **Deploy** group, collapsed by default. ## Skills (runs)

The `skills` page does not poll: it only runs on a click on **Run**. Skills come from `skills.json` next to `settings.json` (read-only; missing or invalid uses the default `/acabativa`):

```json
{
  "schemaVersion": 1,
  "skills": [
    {
      "id": "acabativa",
      "name": "Acabativa",
      "prompt": "/acabativa",
      "maxBudgetUsd": 2,
      "allowedTools": ["Read(./**)", "Bash(gh pr list:*)", "Bash(gh pr view:*)", "Bash(gh pr checks:*)", "Bash(gh pr diff:*)", "Bash(gh search prs:*)"],
      "cwd": null
    }
  ]
}
```

- Command: `claude -p "<prompt>" --output-format stream-json --verbose --max-budget-usd <value> --allowedTools "Read(./**),Bash(gh pr diff:*),…"` through `process_spawn` (no shell; the tool list is a single argument). `--verbose` is required by `stream-json` in `-p` mode. A prompt starting with `-` is rejected. `cwd` must be absolute and without `..`, and must be a project folder: inside the user's folder (not the folder itself), with a `.git` folder or file, and outside `~/Library`, `~/.config`, `~/.kube`, `~/.docker`, `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.claude`, `~/AppData` and the app's own folders; without `cwd` the run starts in `app_cache_dir()/skill-cwd` (on macOS `~/Library/Caches/com.mottu.clawdmeter/skill-cwd`), an empty app folder, and not in the user's folder. Rust appends its own flags (see [SECURITY.md](SECURITY.md#skills-policy-claude--p)): no user, project or local settings, no MCP servers, an app-owned settings file. Skills that read Jira through MCP (the `/acabativa` cards) run without Jira until the app ships its own MCP config.
- Events and `process_kill` use a per-spawn id returned by `process_spawn`, not the pid; when the main process exits, Rust kills whatever it left in its process group (Windows: a kill-on-close Job Object). A run is killed after 15 minutes.

- **Failure without `result` (round 3).** If the process ends without a `result` event, the run fails showing the stderr (last 2000 characters); when a line was truncated, the error is the truncation message followed by the stderr, on another line. Without stderr, the generic message with the exit code applies.
- The stream is read line by line (`process-output`/`process-exit`) and interpreted in `domain/skills` (`parseStreamLine` + `applyStreamEvent`): assistant messages, `result` with cost/duration and `session_id`.
- **Cancel** kills the process group (`process_kill`); cancelling before the process is attached is stored and applied on attach. The history (last 20 runs, without the live log) is kept in `runs.json` in `appConfigDir`, with serialized writes.
- When the run ends (success or failure, never cancelled) a local notification goes out with cost and duration, if the notifications connection is ok.
- **Continue in terminal** opens `claude --resume <session_id>` (the id must be a UUID) in the same folder as the run.
- Problems with a fix button: MCP with `needs-auth`, `pending` or `failed` in the `init` (`mcp_servers[].status`) → **Reconnect MCP** (Terminal with `claude /mcp`); Claude Code missing → **Install Claude Code**.

## Updates

The app updates itself from the GitHub Releases of the private repository named in `RELEASE_REPOSITORY` (`src-tauri/src/commands/updater.rs`, today `rafalibano/clawdmeter`; change this one constant when the repository moves to `Mottu-ops/clawdmeter`).

- **Layers.** `domain/updates` (semver comparison, `UpdateStatus`, banner rule, 6 h schedule and rate-limit window), `application/updates/Updates` (state, timer and use of the GitHub connection through `GitHubSession`), the `UpdateChecker` port, `infrastructure/updates/TauriUpdateChecker` (commands `updater_check`, `updater_install` with a `Channel` for progress, `updater_restart`; version from `getVersion()`, which reads `tauri.conf.json` → `package.json`) and `DemoUpdateChecker` (`?demo=update:available`, `latest`, `no-access`, `rate-limited`, `error`, `install-error`; any `update:` value also connects the demo GitHub unless `github:` is given). The UI has `UpdatesFacade`, the banner at the top of the popover and the collapsible **Updates** section in Settings.
- **When it checks.** On launch and then every 6 h (a 15 min tick looks at the schedule). Without GitHub connected nothing is requested and Settings shows "Connect GitHub to receive updates"; once GitHub is connected the next tick checks. A 403/429 with `x-ratelimit-remaining: 0` or `Retry-After` blocks every check (including **Check now**) until `Retry-After` / `x-ratelimit-reset`, or 1 h when neither header comes.
- **Flow in Rust (`updater_check`).** `GET /repos/<repo>/releases/latest` with the GitHub token → finds the `latest.json` asset → downloads it from `/releases/assets/<id>` (`Accept: application/octet-stream`) → rewrites each `platforms.*.url` (a `github.com/.../releases/download/...` link, which does not accept a token on a private repository) to the API URL of the asset with the same file name, dropping platforms whose file is not in the release → `restore_update` of `tauri-plugin-updater` picks the platform (`darwin-aarch64-app`, `darwin-aarch64`, `windows-x86_64-nsis`, `linux-x86_64-appimage`, …) and compares versions. On Linux `latest.json` has only `linux-x86_64-appimage`: a `.deb` install looks for `linux-x86_64-deb` and then `linux-x86_64`, finds neither and reads as up to date, instead of downloading the AppImage and handing it to `dpkg`. A release without `latest.json`, or without an entry for this platform, means "up to date". The pending `Update` stays in Rust state.
- **Install (`updater_install`).** Downloads the package from the API with the token (progress through the channel), `Update::install` verifies the minisign signature against `plugins.updater.pubkey` (with `requireSignedVersion`, the version in the signed trusted comment must match `latest.json`) and installs: on macOS it replaces the `.app` and the banner asks "Restart now?"; on Windows the installer runs in passive mode and closes the app; on Linux the file at `$APPIMAGE` is replaced and the banner asks to restart. `updater_restart` ends the skill processes and calls `AppHandle::restart`.
- **Redirects.** The HTTP client does not follow redirects on its own. Each hop is checked: `api.github.com` gets `Authorization: Bearer`, the asset storage (`release-assets.githubusercontent.com`, `objects.githubusercontent.com`) is requested without it, any other host or a non-https URL is refused before connecting; at most 3 hops. Limits: release JSON 1 MiB, `latest.json` 64 KiB, package 300 MiB; 20 s timeout for the check and 15 min for the download.

## Launch at login

Settings > **System** has a **Launch at login** switch on macOS, Windows and Linux; on any other system the section is not shown. The app never registers itself: it is off until the user turns it on.

- **State comes from the OS.** Each time Settings opens, the switch reads `launch_at_login_status` from the system; nothing goes into `settings.json` (no schema change). While a change is pending the switch shows the requested value and is disabled; afterwards it shows what the status read returns. The section stays hidden until the first read answers, and also when the read says `supported: false`.
- **Layers.** The `LaunchAtLogin` port (`status()` returning `{ supported, enabled }`, `enable`, `disable`), the `GetLaunchAtLogin` and `SetLaunchAtLogin` use cases (both return `{ supported, enabled, failed }` with `failed` as `'read' | 'write' | false`: a read that throws is `'read'`, keeps the section visible and shows "Could not read the launch at login setting."; a write that throws, or a read-back that works but does not reflect the request, is `'write'`; a write that works and a read-back that throws keeps `'read'` and the state as read and shows "Could not change launch at login. Showing the current system state."; `SetLaunchAtLogin` calls `enable`/`disable` and reads the state back), `infrastructure/platform/TauriLaunchAtLogin` (calls `launch_at_login_status`, `launch_at_login_enable` and `launch_at_login_disable` through `TauriCommands`, without arguments; a reply without boolean fields reads as unsupported and off), `DemoLaunchAtLogin` (in memory, supported, starts off) and, in the UI, `LaunchAtLoginComponent` with a `LaunchAtLoginFacade` scoped to it.
- **Errors.** A failed write, or a read-back that does not match the request, returns the real state with `failed: 'write'`: the switch goes back to the real state and a short message shows under it. A failed read shows off with its own message, also when it follows a successful write; the switch stays usable. The collapsed summary shows "Status unavailable" only after a failed read (or before the first read); after a failed write it shows the real On/Off. The Rust message (for example the one asking to move the app to `/Applications`) is not shown; the UI only distinguishes read from write.
- **Rust (`commands/launch_at_login.rs`).** A `LaunchAtLogin` trait (`status`, `enable`, `disable`) with one implementation per system, picked at compile time with `#[cfg(target_os)]`, on top of the `auto-launch` 0.6 crate (only a dependency on macOS, Windows and Linux). The three commands are `async` and run in `spawn_blocking`.
  - **macOS:** a LaunchAgent (`MacOSLaunchMode::LaunchAgent`) at `~/Library/LaunchAgents/ClawdMeter.plist` (`Label` `ClawdMeter`, `RunAtLoad`, `ProgramArguments` = the canonical path of the running executable inside the `.app`, no arguments) with `AssociatedBundleIdentifiers` = the app identifier read from the Tauri config (`com.mottu.clawdmeter`), so System Settings > Login Items attributes it to ClawdMeter. `enable` refuses with `policy` when the canonical executable path contains `/AppTranslocation/` or starts with `/Volumes/` (the app is running from a temporary copy made by Gatekeeper or from the mounted `.dmg`, a path that disappears), asking to move the app to `/Applications`; the check is the pure function `ensure_stable_location`. When the plist already points at the same executable with the same bundle identifier, `enable` does not rewrite it.
  - **Windows:** the `ClawdMeter` value under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` with the quoted `.exe` path (`WindowsEnableMode::CurrentUser`), never `HKLM`, so turning it off never needs elevation. `status` also honors the Task Manager startup toggle (`StartupApproved\Run`). `disable` also tries to remove an `HKLM` value and ignores the access denial; a `ClawdMeter` value that something else left in `HKLM` still reads as on and needs an elevated app to be removed.
  - **Linux:** an XDG autostart entry, `~/.config/autostart/ClawdMeter.desktop` (`LinuxLaunchMode::XdgAutostart`; `auto-launch` always uses `~/.config`, not `$XDG_CONFIG_HOME`), whose `Exec` is the double-quoted path of the `.AppImage` file (`$APPIMAGE`) when the app runs as an AppImage, otherwise the running executable (`/usr/bin/…` for the `.deb`). `enable` refuses with `policy` an executable under `/tmp/.mount_` without `$APPIMAGE` (the AppImage mount changes on every run) and a path with `"`, `` ` ``, `$`, `\`, `%` or control characters, which the desktop entry quoting cannot hold; the check is the pure function `autostart_exec`. `status` only checks that the file exists.
  - **Other systems:** `status` returns `{ supported: false, enabled: false }`; `enable` and `disable` return `policy`.
  - **Rewrite on launch.** In the Tauri `setup` of release builds (a dev build would repoint the installed app's entry at `target/debug`), a blocking task reads the status and, when it is on, calls `enable` again (`refresh`), so after the user moves the `.app` the agent points at the copy that is running. A failure there (including the location refusal, which keeps the old path) goes to `popover.log` as `launch-at-login refresh …` and never stops the startup.
  - **Limits.** On macOS `status` only checks that the plist exists: an agent turned off in System Settings > General > Login Items, or one whose executable no longer exists, still reads as on. Deleting the app with the switch on leaves the plist behind (see Uninstall in the README).

## Build and release

- `.github/workflows/ci.yml`: on push to `main` and on PR, runs lint, typecheck, Vitest, build, `cargo test`, `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings` on `macos-latest`, `windows-latest` and `ubuntu-22.04` (the Linux job first installs the WebKitGTK, AppIndicator, librsvg, OpenSSL, D-Bus and xdo development packages, and at the end builds the `.AppImage` and `.deb` with `--config '{"bundle":{"createUpdaterArtifacts":false}}'`, since PRs have no signing key, and uploads them as the `clawdmeter-linux-x86_64` artifact for testing); a `supply-chain` job (ubuntu) runs `cargo audit` and `cargo deny check` (`src-tauri/deny.toml`: permissive licenses, advisories and sources only from crates.io).
- `.github/workflows/release.yml`: on a `v*` tag, builds a universal `.app`/`.dmg` (arm64 + x64, macOS 14+), `.msi` + NSIS `.exe` (Windows 10+) and `.AppImage` + `.deb` (Linux x86_64, built on `ubuntu-22.04` for glibc 2.35) with `tauri-apps/tauri-action`, signs the macOS `.app` with the self-signed certificate `ClawdMeter Self-Signed` from the `release` environment (it stops before building when the secrets are missing; see "macOS signing certificate" in `docs/DEVELOPMENT.md`), signs the updater artifacts with `TAURI_SIGNING_PRIVATE_KEY` (`.app.tar.gz.sig`, `.msi.sig`, `.exe.sig`, `.AppImage.sig`) and uploads them to a draft release (`releaseId` from the `draft` job, which refuses an already published tag); the final `publish` job builds `latest.json` once from the draft's `.sig` files (`tools/release/latest-json.mjs`, the v0.2.2 keys plus `linux-x86_64-appimage`), uploads it and publishes the draft only when every platform passed.
- **Permissions and pins.** `ci.yml` runs with `permissions: contents: read`; `release.yml` has `permissions: {}` at the top and `contents: write` only on its three jobs (they create, fill and publish the release). Every `actions/checkout` uses `persist-credentials: false`, so the token is not stored in the jobs' `.git`. All actions are pinned by commit SHA, with the version in a `# vN` comment next to it: `actions/checkout` v4.4.0, `actions/setup-node` v4.4.0, `swatinem/rust-cache` v2.9.3, `taiki-e/install-action` v2.90.1, `tauri-apps/tauri-action` v0.6.2 and `dtolnay/rust-toolchain` on the `stable` branch (the action derives the toolchain from the ref name, and a SHA does not carry that name, so `toolchain:` is explicit). Dependabot (`.github/dependabot.yml`) opens weekly PRs for `github-actions`, `cargo` (`/src-tauri`) and `npm`, and updates the SHA together with the comment. The SHAs were checked with `gh api repos/<org>/<repo>/commits/<sha>` and `…/tags`. A test (`tools/workflows.spec.ts`) fails if an action leaves the SHA pin, loses the version comment, or if a checkout loses `persist-credentials: false`.
- **Pinned Rust toolchain.** `rust-toolchain.toml` (root) pins `1.99.1`, the stable version installed on the development machine (`rustc 1.99.1`, 2026-10-13), with `clippy` and `rustfmt`; CI and release pass `toolchain: 1.99.1` to the action and the same test requires the values to match. To bump the version, change the `channel` and the `toolchain:` values together.

To publish: bump the version in `package.json` and `src-tauri/Cargo.toml` (`tauri.conf.json` reads the version from `package.json`), and create the tag.

```bash
git tag v0.1.0 && git push origin v0.1.0
```

### Migration from the old identifier

Up to 0.1.0 the app used the identifier `com.mottu.devpulse`. On the first launch with `com.mottu.clawdmeter` (`legacy_migration.rs`, in the Tauri `setup`, before the log and before the webview reads any config):

- **Files:** if the new config folder (`~/Library/Application Support/com.mottu.clawdmeter` on macOS, `%APPDATA%\com.mottu.clawdmeter` on Windows) does not exist or is empty and the old one (`…/com.mottu.devpulse`) exists, the top-level files of the old one (`settings.json`, `usage-history.json`, `connections.json`, `runs.json`, `skills.json` and the like; ignores `*.tmp`, hidden files and subfolders) are **copied** to a temporary folder `com.mottu.clawdmeter.migrating`, which is renamed to the new folder in one go; only then is the `.legacy-config-migrated` marker written. The old folder is not deleted. With the marker present (or the old marker inside the config folder, from earlier builds), or with the new folder already in use, nothing happens.
- **Secrets:** on the first call of `secret_get/set/delete`, each key of `ALLOWED_SECRET_KEYS` that does not exist in the `com.mottu.clawdmeter` service and exists in `com.mottu.devpulse` is read (reassembling the `dp-chunked:v1:` slices), written to the new service and then **deleted** from the old one (best effort). The `.legacy-secrets-migrated` marker prevents a second copy (a logout is not undone on the next launch). The marker is written on success and also when the Keychain refuses the read (kept apart inside Rust, reported to TS as `keychain`), so a denied prompt is not shown again on every launch; any other Keychain error is retried on the next launch. An install that migrated with an older build (marker in the config folder) only gets the stale old items deleted, once. The Claude account tokens (`claude.account.<accountId>`) are not in `ALLOWED_SECRET_KEYS` and are not migrated.
- **Markers:** both markers live in `app_data_dir()/.migration/` (on macOS the same folder as `$APPCONFIG`). A global `fs:scope` deny on `$APPDATA/.migration` and `$APPDATA/.migration/**` in `capabilities/default.json` keeps every webview `fs` command away from them, so the webview cannot rename a marker to trigger a re-import (checked by a Rust test and `tools/capabilities.spec.ts`).
- **Logs:** `popover.log` is now written to the new `app_log_dir()` (`~/Library/Logs/com.mottu.clawdmeter` on macOS); the result of the two migrations is recorded in it (`legacy-config …`, `legacy-secrets …`).
- The `dp-chunked:v1:` header of the sliced secrets is a persisted format and keeps the old name.
